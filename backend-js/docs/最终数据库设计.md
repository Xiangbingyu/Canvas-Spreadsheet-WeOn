# 最终数据库设计

## 1. 设计目标

本文档基于以下两份文档整理最终数据库设计：

- `backend-js/docs/UndoRedo方案简述.md`
- `backend-js/docs/后端分层职责简述.md`

目标如下：

- 一期内存结构直接对标二期数据库结构
- 支持 `set_cell`、`import_sheet`、`undo`、`redo`
- 支持单元格值与单元格样式共同存储
- 支持后续审计、在线用户、连接记录扩展

## 2. 最终表清单

最终建议保留 6 张表：

- `doc`
- `history`
- `user_op_state`
- `audit_log`
- `room_user`
- `room_socket`

其中：

- 核心主数据表：
  - `doc`
  - `history`
  - `user_op_state`
- 审计支持表：
  - `audit_log`
- 协同运行态表：
  - `room_user`
  - `room_socket`

## 3. 表设计

### 3.1 `doc`

用途：

- 保存文档当前最新状态
- 每个文档只保留一条当前记录

建议字段：

- `id`
  - 类型：`BIGINT`
  - 说明：自增主键
- `doc_id`
  - 类型：`VARCHAR(64)`
  - 说明：业务文档 ID
- `title`
  - 类型：`VARCHAR(255)`
  - 说明：文档标题
- `snapshot_json`
  - 类型：`JSON`
  - 说明：当前完整文档快照
- `current_seq`
  - 类型：`BIGINT`
  - 说明：当前文档最新全局序号
- `created_by`
  - 类型：`VARCHAR(64)`
  - 说明：创建人，可为空
- `created_at`
  - 类型：`DATETIME`
  - 说明：创建时间
- `updated_at`
  - 类型：`DATETIME`
  - 说明：更新时间

约束建议：

- 主键：`id`
- 唯一键：`uk_doc_id (doc_id)`

说明：

- `snapshot_json` 保存当前文档所有单元格值和样式
- 每次 `set_cell`、`import_sheet`、`undo`、`redo` 成功后，都更新这张表

### 3.2 `history`

用途：

- 保存文档全局真实落地历史
- `undo/redo` 的核心依赖表
- 采用 append-only，不回写旧记录

建议字段：

- `id`
  - 类型：`BIGINT`
  - 说明：自增主键
- `doc_id`
  - 类型：`VARCHAR(64)`
  - 说明：所属文档 ID
- `seq`
  - 类型：`BIGINT`
  - 说明：文档级全局递增序号
- `client_id`
  - 类型：`VARCHAR(64)`
  - 说明：操作用户 ID
- `op_type`
  - 类型：`VARCHAR(32)`
  - 说明：操作类型
- `target_row`
  - 类型：`INT`
  - 说明：目标行，可为空
- `target_col`
  - 类型：`INT`
  - 说明：目标列，可为空
- `old_value_json`
  - 类型：`JSON`
  - 说明：修改前值，可为空
- `new_value_json`
  - 类型：`JSON`
  - 说明：修改后值，可为空
- `old_style_json`
  - 类型：`JSON`
  - 说明：修改前样式，可为空
- `new_style_json`
  - 类型：`JSON`
  - 说明：修改后样式，可为空
- `payload_json`
  - 类型：`JSON`
  - 说明：完整操作载荷
- `source_seq`
  - 类型：`BIGINT`
  - 说明：若当前操作是 `undo/redo`，记录其对应的原始操作序号
- `event_id`
  - 类型：`VARCHAR(128)`
  - 说明：幂等事件 ID，可为空
- `created_at`
  - 类型：`DATETIME`
  - 说明：创建时间

约束建议：

- 主键：`id`
- 唯一键：`uk_doc_seq (doc_id, seq)`
- 普通索引：`idx_history_doc_client (doc_id, client_id)`
- 普通索引：`idx_history_source_seq (doc_id, source_seq)`
- 可选唯一键：`uk_event_id (event_id)`，取决于最终幂等策略

推荐 `op_type`：

- `set_cell`
- `import_sheet`
- `undo`
- `redo`
- 后续可扩展：
  - `set_style`

说明：

- `history` 是全局协同事件流
- `undo/redo` 不是回退旧记录，而是新增一条新记录

### 3.3 `user_op_state`

用途：

- 保存每个用户在每个文档上的 `undo/redo` 状态
- 对应 B 方案中的 `undoStack` / `redoStack`

建议字段：

- `id`
  - 类型：`BIGINT`
  - 说明：自增主键
- `doc_id`
  - 类型：`VARCHAR(64)`
  - 说明：所属文档 ID
- `client_id`
  - 类型：`VARCHAR(64)`
  - 说明：用户 ID
- `undo_stack_json`
  - 类型：`JSON`
  - 说明：当前可撤销操作栈
- `redo_stack_json`
  - 类型：`JSON`
  - 说明：当前可重做操作栈
- `updated_at`
  - 类型：`DATETIME`
  - 说明：更新时间

约束建议：

- 主键：`id`
- 唯一键：`uk_doc_client (doc_id, client_id)`

说明：

- 栈元素建议直接保存完整操作快照
- 这样 `undo/redo` 时不必再反查全部历史
- 如果未来数据量变大，再考虑拆成更细粒度结构

### 3.4 `audit_log`

用途：

- 保存关键业务事件审计日志
- 不参与主业务状态收敛，但用于排错、追踪和运营审计

建议字段：

- `id`
  - 类型：`BIGINT`
  - 说明：自增主键
- `event_type`
  - 类型：`VARCHAR(64)`
  - 说明：审计事件类型
- `doc_id`
  - 类型：`VARCHAR(64)`
  - 说明：关联文档 ID，可为空
- `client_id`
  - 类型：`VARCHAR(64)`
  - 说明：关联用户 ID，可为空
- `request_id`
  - 类型：`VARCHAR(128)`
  - 说明：请求 ID，可为空
- `payload_json`
  - 类型：`JSON`
  - 说明：完整审计数据
- `created_at`
  - 类型：`DATETIME`
  - 说明：记录时间

约束建议：

- 主键：`id`
- 普通索引：`idx_audit_doc (doc_id)`
- 普通索引：`idx_audit_client (client_id)`
- 普通索引：`idx_audit_event_type (event_type)`

推荐 `event_type`：

- `doc_created`
- `join`
- `leave`
- `presence`
- `set_cell`
- `import_sheet`
- `undo`
- `redo`

### 3.5 `room_user`

用途：

- 保存房间在线用户或房间成员状态
- 主要服务于协同在线状态与 `presence`

建议字段：

- `id`
  - 类型：`BIGINT`
  - 说明：自增主键
- `doc_id`
  - 类型：`VARCHAR(64)`
  - 说明：所属文档 ID
- `client_id`
  - 类型：`VARCHAR(64)`
  - 说明：用户 ID
- `name`
  - 类型：`VARCHAR(128)`
  - 说明：显示名称
- `color`
  - 类型：`VARCHAR(32)`
  - 说明：用户颜色
- `status`
  - 类型：`VARCHAR(32)`
  - 说明：在线状态，如 `online`、`offline`
- `joined_at`
  - 类型：`DATETIME`
  - 说明：加入时间
- `last_active_at`
  - 类型：`DATETIME`
  - 说明：最后活跃时间

约束建议：

- 主键：`id`
- 唯一键：`uk_room_user (doc_id, client_id)`

说明：

- 单机演示阶段这张表也可以先用内存
- 多实例协同时，这张表或其等价缓存会更有意义

### 3.6 `room_socket`

用途：

- 保存连接记录或连接元信息
- 注意：这里记录的是连接元数据，不是真实 WebSocket 对象

建议字段：

- `id`
  - 类型：`BIGINT`
  - 说明：自增主键
- `doc_id`
  - 类型：`VARCHAR(64)`
  - 说明：所属文档 ID
- `client_id`
  - 类型：`VARCHAR(64)`
  - 说明：用户 ID
- `connection_id`
  - 类型：`VARCHAR(128)`
  - 说明：连接唯一标识
- `server_id`
  - 类型：`VARCHAR(128)`
  - 说明：所在服务实例 ID，可为空
- `status`
  - 类型：`VARCHAR(32)`
  - 说明：连接状态，如 `connected`、`closed`
- `connected_at`
  - 类型：`DATETIME`
  - 说明：连接建立时间
- `last_active_at`
  - 类型：`DATETIME`
  - 说明：最后活跃时间

约束建议：

- 主键：`id`
- 唯一键：`uk_connection_id (connection_id)`
- 普通索引：`idx_room_socket_doc_client (doc_id, client_id)`

说明：

- 如果后续生产环境不打算将连接信息持久化到 MySQL，也可以将它替换为 Redis/内存实现
- 但为了“一期内存结构直接对标二期数据库结构”，这里仍建议保留

## 4. 表关系

建议关系如下：

- `doc.doc_id` 为业务文档主键
- `history.doc_id` 关联 `doc.doc_id`
- `user_op_state.doc_id` 关联 `doc.doc_id`
- `room_user.doc_id` 关联 `doc.doc_id`
- `room_socket.doc_id` 关联 `doc.doc_id`
- `audit_log.doc_id` 可选关联 `doc.doc_id`

说明：

- 这里更偏业务主键关联，而不是完全依赖自增 `id`
- 协同系统里 `doc_id` 更适合作为跨表业务定位字段

## 5. 单元格值与样式设计

单元格不仅有值，还会有样式，因此样式会直接影响数据库设计。

当前建议：

- 当前文档状态放入 `doc.snapshot_json`
- 历史变更放入 `history.old_value_json`、`new_value_json`、`old_style_json`、`new_style_json`、`payload_json`
- `user_op_state` 栈元素也要保存值变化和样式变化

### 5.1 单元格推荐结构

```json
{
  "value": "123",
  "style": {
    "fontSize": 14,
    "bold": true,
    "italic": false,
    "underline": false,
    "color": "#111111",
    "backgroundColor": "#ffffff",
    "align": "center"
  }
}
```

### 5.2 文档快照推荐结构

```json
{
  "cells": {
    "1:1": {
      "value": "姓名",
      "style": {
        "fontSize": 14,
        "bold": true,
        "italic": false,
        "underline": false,
        "color": "#111111",
        "backgroundColor": "#ffffff",
        "align": "center"
      }
    }
  },
  "styles": {},
  "rowCount": 100,
  "colCount": 26
}
```

### 5.3 `history.payload_json` 推荐结构

```json
{
  "row": 1,
  "col": 1,
  "oldValue": "张三",
  "newValue": "李四",
  "oldStyle": {
    "fontSize": 12,
    "bold": false,
    "italic": false,
    "underline": false,
    "color": "#111111",
    "backgroundColor": "#ffffff",
    "align": "left"
  },
  "newStyle": {
    "fontSize": 14,
    "bold": true,
    "italic": false,
    "underline": false,
    "color": "#ff0000",
    "backgroundColor": "#ffff00",
    "align": "center"
  }
}
```

说明：

- 当前阶段不建议单独拆“样式表”
- 值与样式一起放在 JSON 中，更适合当前协同和 `undo/redo` 设计

## 6. Undo/Redo 对数据库的影响

### 6.1 `history`

- `undo/redo` 都会新增一条 `history`
- 不会回退旧记录
- 不会删除旧记录

### 6.2 `doc`

- `undo/redo` 成功后，会更新 `doc.snapshot_json`
- `current_seq` 同时更新到最新

### 6.3 `user_op_state`

- 每次普通编辑：
  - 压入 `undo_stack_json`
  - 清空 `redo_stack_json`
- 每次 `undo`：
  - 从 `undo_stack_json` 弹出
  - 压入 `redo_stack_json`
- 每次 `redo`：
  - 从 `redo_stack_json` 弹出
  - 压回 `undo_stack_json`

## 7. 一期内存与二期数据库映射

一期内存结构建议直接映射如下：

- `doc` -> `store/docStore.js` + `store/memory/docMemoryStore.js`
- `history` -> `store/historyStore.js` + `store/memory/historyMemoryStore.js`
- `user_op_state` -> `store/userOpStateStore.js` + `store/memory/userOpStateMemoryStore.js`
- `room_user` -> `store/roomUserStore.js` + `store/memory/roomUserMemoryStore.js`
- `room_socket` -> `store/roomSocketStore.js` + `store/memory/roomSocketMemoryStore.js`
- `audit_log` -> `store/auditLogStore.js` + `store/memory/auditLogMemoryStore.js`

这样二期切 MySQL 时：

- `service` 层尽量不动
- `domain/entities` 尽量不动
- 主要替换 `store` 层实现即可

## 8. 建议总结

最终数据库建议就按以下 6 张表收口：

- `doc`
- `history`
- `user_op_state`
- `audit_log`
- `room_user`
- `room_socket`

其中最终原则是：

- `doc` 保存当前状态
- `history` 保存全局真实历史
- `user_op_state` 保存用户私有 `undo/redo` 状态
- `audit_log` 保存审计事件
- `room_user` 保存在线用户状态
- `room_socket` 保存连接元信息
- 单元格值和样式统一进入 JSON 结构，不先拆成大量字段表
