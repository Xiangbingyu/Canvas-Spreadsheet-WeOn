# 一期实施规划

## 1. 文档目标

本文档用于明确 `Canvas-Spreadsheet-WeOn` 后端一期的实际落地范围。

当前已经完成：

- 最终数据库结构设计
- 后端分层职责设计
- `domain` / `store` 按数据库结构对齐

本期接下来要做的不是把所有规划一次性做完，而是先完成最小可运行闭环，同时为后续 `audit` 与 `undo/redo` 留好接口和结构。

## 2. 一期范围总原则

一期原则如下：

- 先完成核心协同闭环
- 先用内存实现，但结构直接对标二期数据库
- 本期不实现 `audit`
- 本期不实现 `undo`
- 本期不实现 `redo`
- 本期保留 `audit`、`undo/redo` 对应文件、实体、store 和后续接入位置
- 本期默认不主动抽取公共方法
- 如果后续代码确实需要抽取，由用户明确提出后再进行抽取

这里的“核心协同闭环”指：

- 创建文档
- 加入房间
- 查询/广播在线用户
- 单元格编辑
- 整表导入
- 文档当前状态读取

## 3. 一期必须完成的功能

### 3.1 HTTP

本期完成：

- `GET /health`
- `POST /docs`
- 按需补充文档状态读取接口

本期目标：

- 能创建文档
- 能返回文档基础信息和初始快照

### 3.2 WebSocket

本期完成：

- `join`
- `presence`
- `set_cell`
- `import_sheet`

本期暂不实现：

- `undo`
- `redo`

说明：

- `undo` / `redo` 的 handler 文件可以保留
- 但本期只保留占位和错误返回，不进入正式业务闭环

### 3.3 Service

本期完成：

- `docsService`
- `roomService`
- `presenceService`
- `cellService`
- `importService`
- `collabService`
- `healthService`

本期保留但不完整实现：

- `undoRedoService`
- `auditService`

要求：

- `service` 层统一收口业务逻辑
- `routes` / `ws` 只负责入参接收、调用 `service`、返回响应

## 4. 一期数据落地范围

### 4.1 本期实际使用的表模型

本期业务真正使用并写入的结构：

- `doc`
- `history`
- `room_user`
- `room_socket`

用途如下：

- `doc`：保存当前文档状态
- `history`：保存 `set_cell`、`import_sheet` 的真实落地历史
- `room_user`：保存房间在线用户状态
- `room_socket`：保存连接元信息和运行时连接映射

### 4.2 本期保留但暂不启用的表模型

本期保留结构，但暂不进入主流程：

- `user_op_state`
- `audit_log`

用途如下：

- `user_op_state`：为后续 `undo/redo` 预留
- `audit_log`：为后续审计日志预留

要求：

- `domain/entities` 中继续保留对应实体
- `store` 中继续保留对应 store
- 当前业务流程不强制写入这两类数据

### 4.3 一期历史记录范围

本期 `history` 只要求记录：

- `set_cell`
- `import_sheet`

本期不要求记录：

- `undo`
- `redo`

说明：

- 虽然数据库设计支持完整 `undo/redo`
- 但一期只先把普通编辑历史打通

## 5. 一期代码实现约束

### 5.1 关于抽取公共方法

当前阶段默认规则：

- 不主动抽取公共 helper
- 不主动新增 `shared.js`
- 不主动新增为了复用而存在的中间 util
- 优先把当前逻辑直接写在所属文件中

只有在以下情况才考虑抽取：

- 用户明确提出要抽取
- 或用户明确要求整理结构

### 5.2 关于 `domain`

要求：

- `domain/entities/` 只放和真实数据库表一一对应的实体
- 不在 `entities` 里新增非实体性质的公共辅助文件
- 非落库结构继续放 `domain/valueObjects/`

### 5.3 关于 `store`

要求：

- `store` 的内存实现要按“数据库表”思路组织
- 要体现主键、唯一键、复合键和查询入口语义
- 允许为运行时能力保留少量附加结构
- 但附加结构不能替代表模型本身

对 `room_socket` 的特殊说明：

- 表模型保存连接元信息
- 运行时真实 socket 映射只作为一期内存态补充
- 后续切 MySQL 时，表模型保留，运行时映射可继续留在内存或迁移到 Redis

## 6. 一期实施顺序

建议按以下顺序推进：

1. 完成 `docsService`，打通创建文档和读取文档状态
2. 完成 `roomService` 和 `presenceService`，打通加入房间与在线用户同步
3. 完成 `collabService`，统一处理 `seq` 分配、基础广播载荷整理
4. 完成 `cellService`，打通 `set_cell -> history -> doc`
5. 完成 `importService`，打通 `import_sheet -> history -> doc`
6. 联调 `routes` 与 `ws`
7. 最后补齐本期范围内的错误处理和基础校验

## 7. 一期完成标准

满足以下条件即可认为一期核心闭环完成：

- 可以创建文档
- 可以加入指定文档房间
- 可以拿到当前在线用户
- 可以编辑单元格并更新当前文档快照
- 可以导入整表并替换当前文档快照
- `history` 能记录普通编辑历史
- 当前代码结构仍然保留 `audit`、`undo/redo` 的后续接入位置

## 8. 二期衔接方式

二期再继续接入：

- `undo`
- `redo`
- `user_op_state` 的正式读写
- `audit_log` 的正式写入
- MySQL 持久化实现

到二期时应尽量保持：

- `service` 层接口不大改
- `domain/entities` 不大改
- 主要替换 `store` 的底层实现和补充延期业务流程
