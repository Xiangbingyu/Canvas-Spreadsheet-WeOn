# 二期优化方案

## 1. 文档目标

本文档用于整理 `Canvas-Spreadsheet-WeOn` 后端二期优化方向，明确以下五个改造点的目标、实施内容、注意事项与建议顺序：

- 接入 `MySQL`，替换当前核心内存存储
- 接入 `Redis`，承接共享运行态与缓存能力
- 优化当前 `seq` + 后写覆盖方案，并评估消息队列 / `OT` / `CRDT`
- 升级为多实例部署形态
- 在共享状态稳定后接入应用内存，形成三级缓存

本文档的重点不是一次性把所有技术都堆上去，而是给出一个更稳的二期演进路径，尽量避免因为系统复杂度增长过快而影响已有功能。

## 2. 当前一期现状

当前后端已经具备单机内存版协同闭环，主要特点如下：

- 当前文档快照由 `docStore` 维护
- 操作历史由 `historyStore` 维护
- 用户级 `undo/redo` 状态由 `userOpStateStore` 维护
- 房间在线用户和连接元数据由 `roomUserStore`、`roomSocketStore` 维护
- `set_cell`、`import_sheet`、`undo`、`redo` 都已具备基础业务流程
- 当前底层实现仍以内存为主，适合单机开发和演示，不适合直接扩展为分布式多实例

因此，二期的核心任务不是继续往单机内存上叠功能，而是把“状态真相”从应用内存中迁出，使系统具备持久化、共享状态和多实例运行能力。

## 3. 二期总体原则

- 先完成状态外移，再推进分布式部署
- 先保证一致性和可恢复性，再做性能优化
- 先让现有 `seq + history + undo/redo` 在共享存储上跑通，再评估是否必须引入 `OT/CRDT`
- 优先保持现有 `service` 层接口稳定，主要替换 `store` 层与运行态承载方式
- 缓存优化必须建立在共享状态正确的前提之上，不能让缓存反过来成为新的状态真相

## 3.1 当前落地进展

截至当前版本，二期已经不再只是“规划”，而是已经完成了前半段关键落地：

- `MySQL` 已接入，并支持通过环境变量在 `memory/mysql` 之间切换
- `doc.current_seq`、`history.append`、`userOpState.saveState` 已收口到同一 `MySQL` 事务
- `Redis Pub/Sub` 已接入，`join`、`set_cell`、`set_title`、`import_sheet`、`undo`、`redo` 已支持跨实例广播
- `Redis` 缓存层已完成第一批基础闭环：
  - `doc snapshot`
  - `doc meta`
  - `user docs list`
- 幂等键与分布式锁已接入 `Redis` 驱动，并保持 `memory` 链路可回退
- 运行态迁移已经从“规划”推进到“初版落地”，当前已覆盖 `roomSocketStore` 与组合式 `roomUserStore`
- `roomSocketStore`、`roomUserStore` 已支持 `memory/redis` 或 `mysql + redis(runtime)` 组合切换，默认仍保留 `memory` 单机链路
- 多实例 `presence` 一致性、同一 `clientId` 跨实例多连接 fully-offline 判断，已经有自动化测试覆盖
- 最小服务端 `OT / rebase` 已落地：
  - `set_cell` 支持 `baseSeq`
  - `set_title` 支持 `baseSeq`
  - `undo/redo` 已纳入基于 `sourceSeq` 的服务端重放语义
  - `import_sheet` 已作为 OT barrier 生效

当前的实现策略不是一次性彻底替换所有内存运行态，而是采用“驱动切换 + 渐进迁移”的方式：

- 权威业务状态以 `MySQL` 为主
- 跨实例广播与共享运行态以 `Redis` 为主
- 原有 `memory` 链路继续保留，作为单机模式和安全回退路径

## 3.2 当前阶段判断

结合当前代码和测试结果，二期前几个改造点的状态可以归纳如下：

- 改造点一 `MySQL`：已完成基础落地，并已覆盖 `docs/ws` 主链路
- 改造点二 `Redis`：已完成基础接入，已承接跨实例广播、共享运行态、幂等键、分布式锁和第一批热点缓存
- 改造点三 `seq` 一致性增强：已完成事务边界收口与最小服务端 `OT / rebase` 落地，但尚未进入完整 `OT/CRDT` 形态
- 改造点四多实例：已完成“可运行、可广播、可验证”的第一阶段，还未做到完整生产级治理
- 改造点五三级缓存：尚未开始，不应提前推进

换句话说，当前系统已经从“单机内存协同 demo”进入“`MySQL + Redis` 二期基础设施已落地并通过核心回归”的阶段，但还没有进入“全部运行态完全外移 + 生产级多实例治理全部收口”的最终形态。

## 3.3 当前配置原则

为了保证迁移过程中不破坏既有链路，当前配置遵循以下原则：

- `STORE_DRIVER` 控制核心存储走 `memory/mysql`
- `CACHE_DRIVER` 控制缓存走 `memory/redis`
- `RUNTIME_STATE_DRIVER` 控制运行态走 `memory/redis`
- `COLLAB_BROADCAST_DRIVER` 控制广播走 `memory/redis`
- `IDEMPOTENCY_DRIVER` 控制幂等键走 `memory/redis`
- `DOC_LOCK_DRIVER` 控制关键写路径文档锁走 `memory/redis`
- `.env.example` 默认保留 `memory`，避免示例环境直接切到分布式形态
- 本地 `.env` 可切到 `mysql + redis` 组合，用于真实联调和多实例验证

这意味着当前系统已经支持以下几种典型运行方式：

- `memory + memory`：单机开发 / 回归链路
- `mysql + memory`：持久化验证链路
- `mysql + redis(runtime) + redis(broadcast)`：多实例与共享运行态验证链路

## 4. 建议实施顺序

建议按以下顺序推进二期改造：

1. 完成 `MySQL` 落库，替换核心内存 `store`
2. 完成 `Redis` 接入，承接共享运行态、分布式锁与热点缓存
3. 完成跨实例广播和路由能力，使系统具备多实例运行条件
4. 优化全局 `seq` 分配与冲突收敛策略，必要时再评估消息队列和 `OT/CRDT`
5. 在状态共享稳定后接入应用内存，形成三级缓存

这个顺序的原因是：

- 如果没有 `MySQL` 和 `Redis`，多实例没有统一状态基础
- 如果没有统一状态基础，消息队列也无法真正解决一致性问题
- 如果一致性和恢复能力尚未收敛，三级缓存会放大排查难度

## 5. 改造点一：接入 MySQL，替换核心内存存储

### 5.1 改造目标

将当前以内存实现的核心业务数据迁移到 `MySQL`，使系统具备真正的持久化能力，并为多实例共享状态提供权威数据源。

### 5.2 建议承接的数据

优先迁移以下结构：

- `doc`
- `history`
- `user_op_state`
- `audit_log`
- `room_user`

其中：

- `doc` 保存文档当前快照与 `current_seq`
- `history` 保存全局真实历史，采用 append-only
- `user_op_state` 保存每用户每文档的 `undoStack/redoStack`
- `audit_log` 保存关键业务审计事件
- `room_user` 保存用户在文档中的在线 / 离线状态

### 5.3 实施内容

- 新增 `MySQL` 连接配置和数据源管理
- 按现有文档设计建立核心表结构
- 替换 `store/memory/*` 的核心实现
- 保持 `service` 层调用方式尽量不变
- 为 `doc`、`history`、`user_op_state` 增加必要索引
- 增加迁移脚本、初始化脚本和基础回滚方案

### 5.4 需要注意的地方

- 不要一上来就把所有运行态都放进 `MySQL`，应优先让核心真相数据先稳定
- `history` 必须坚持 append-only，避免覆盖或修改旧历史
- `doc.current_seq` 必须和当前快照更新保持一致，不能出现快照已更新但序号未推进的情况
- `user_op_state` 的写入要和当前操作结果相匹配，避免 `undo/redo` 栈与真实文档状态脱节
- 数据库事务边界要清晰，至少要保证“当前快照更新”和“对应历史追加”不会半成功半失败
- 表结构设计时要提前考虑分页查询、按文档查询历史、按用户查询操作状态等常见访问路径

### 5.5 阶段完成标准

- 服务重启后文档状态不丢失
- `set_cell`、`import_sheet`、`undo`、`redo` 不再依赖本地内存 `store`
- 可以从数据库中恢复出当前快照、历史记录和用户操作状态

### 5.6 当前完成情况

本阶段当前已经达到以下状态：

- `doc`、`history`、`user_op_state`、`audit_log`、`room_user` 已具备 `MySQL` 实现
- 测试前支持清库并恢复系统种子数据
- `docs.test.js` 和 `ws.test.js` 已能在 `MySQL` 环境下稳定运行
- `doc.current_seq`、`history.append`、`userOpState.saveState` 已放入同一事务

因此，改造点一可以视为“基础完成并已通过主链路验证”。

## 6. 改造点二：接入 Redis，承接共享运行态和缓存

### 6.1 改造目标

将当前由应用内存直接维护的共享运行态迁移到 `Redis`，为多实例提供共享状态、快速访问和分布式协调能力。

### 6.2 建议承接的能力

建议优先放入 `Redis` 的内容如下：

- 热点文档快照缓存
- 当前文档的 `seq` 或序号分配辅助结构
- 幂等键
- 分布式锁
- 在线用户索引
- 房间成员关系
- 连接元数据，如 `connectionId -> docId/clientId/serverId`

### 6.3 实施内容

- 新增 `Redis` 客户端与统一封装
- 把当前 `room` 相关共享运行态从本机内存迁移到 `Redis`
- 把幂等控制迁移到 `Redis`
- 引入分布式锁能力，服务于关键写路径
- 为热点数据设计合理的过期时间和失效策略

### 6.4 需要注意的地方

- 真实 `WebSocket` 对象不能放进 `Redis`，只能存连接元信息
- `Redis` 适合承接共享运行态和缓存，不应取代 `MySQL` 作为最终权威历史存储
- 锁要有过期时间和续期策略，避免死锁或长时间占锁
- 幂等键和锁的键设计要统一规范，避免不同业务互相污染
- 缓存失效时必须能回源到 `MySQL`，不能让缓存成为唯一数据来源
- 如果把 `seq` 放到 `Redis` 原子递增，要明确它和数据库最终事务提交之间的关系

### 6.5 阶段完成标准

- 多个应用实例可以共享在线状态、幂等信息和热点快照
- 房间相关运行态不再依赖单台应用的本地内存
- 单个实例重启不会导致共享运行态完全失效

### 6.6 当前完成情况

当前这一阶段已完成的内容主要包括：

- 已新增 `infra/redis/client.js`、`infra/redis/pubsub.js`
- 已新增统一缓存封装、key 规范与 TTL 配置
- 已新增 `RUNTIME_STATE_DRIVER`，允许运行态在 `memory/redis` 之间切换
- 已新增 `CACHE_DRIVER`、`IDEMPOTENCY_DRIVER`、`DOC_LOCK_DRIVER`
- 已将 `roomSocketStore` 迁移为可切换的 `memory/redis` 双驱动结构
- 已将 `roomUserStore` 收口为组合式实现：
  - 持久参与关系走 `MySQL`
  - 在线运行态走 `Redis`
- Redis 运行态当前主要承接：
  - `connectionId -> docId/clientId/serverId`
  - `(docId, clientId)` 连接集合
  - 房间在线用户运行态索引
  - fully-offline 判断基础
- Redis 当前还已承接：
  - `doc snapshot` 缓存
  - `doc meta` 缓存
  - `user docs list` 缓存
  - `POST /docs` 幂等键
  - 文档级分布式锁
- 已保留本地 socket 对象映射，避免把真实 `WebSocket` 对象写入 `Redis`
- 已补充 Redis 链路自动化测试，覆盖缓存回源/失效、跨实例广播、presence、一部分 OT 场景和 room runtime 行为

需要明确的是，改造点二目前可以视为“共享运行态 + 第一批缓存基础设施已完成”，但并不是“所有运行态都已经 100% 外移”，也不是“生产级容量治理和观测能力已全部收口”。

### 6.7 第一批 Redis 缓存改造清单

考虑到当前准备“尽量一次改完基础设施”，第一批缓存改造不建议零散推进，而应一次性把基础规范、缓存对象、失效规则和测试口径同时补齐。

这一批的目标不是把所有状态都搬进 `Redis`，而是完成“共享运行态 + 低风险热点缓存”的基础闭环。

#### 6.7.1 改造目标

- 让高频读取优先命中 `Redis`
- 让缓存 miss 时可以稳定回源 `MySQL`
- 让所有写路径都有明确的缓存失效策略
- 让现有 `memory/mysql/redis` 链路继续保持兼容
- 为后续应用内存一级缓存预留统一键规范和失效机制

#### 6.7.2 本批次必须新增的基础能力

- 新增统一的 `Redis` 缓存 key 规范
- 新增统一的缓存序列化 / 反序列化封装
- 新增统一的缓存 TTL 配置
- 新增统一的缓存读取辅助方法，例如：
  - cache-aside / read-through
  - miss 回源后回填
- 新增统一的缓存失效辅助方法，例如：
  - 单 key 删除
  - 批量 key 删除
  - 按文档删除关联缓存
  - 按用户删除关联列表缓存
- 明确区分：
  - 权威真相数据
  - 共享运行态
  - 只读缓存数据

#### 6.7.3 本批次建议先接入 Redis 的数据

第一批建议接入以下缓存或共享运行态：

- 文档快照缓存
  - key：`collab:doc:snapshot:{docId}`
  - 内容：`docId`、`title`、`sheetData`、`currentSeq`、`updatedAt`
  - 用途：优先服务 `GET /docs/:docId` 和写后回读
- 文档元信息缓存
  - key：`collab:doc:meta:{docId}`
  - 内容：文档标题、创建者、更新时间、当前版本摘要
  - 用途：服务轻量详情读取和后续列表聚合
- 用户文档列表缓存
  - key：`collab:user:docs:{userId}:{page}:{limit}`
  - 内容：创建文档列表、参与文档列表或合并后的结果
  - 用途：降低文档列表查询压力
- 在线运行态索引
  - `connectionId -> docId/clientId/serverId`
  - `docId -> connections`
  - `docId + clientId -> connections`
  - 用途：跨实例在线态、fully-offline 判断、presence 组装
- 幂等键
  - key：`collab:idempotency:{eventId}`
  - 用途：重复请求去重

#### 6.7.4 本批次明确不进入 Redis 真相层的数据

以下内容在本批次不应作为 `Redis` 主状态接入：

- `undo/redo` 栈权威状态
  - 当前继续以 `MySQL user_op_state` 为准
- 全量 `history`
  - 当前继续以 `MySQL append-only` 为准
- 审计日志真相
  - 当前继续以 `MySQL audit_log` 为准
- 事务中间态
  - 例如快照已更新但 `history/user_op_state` 尚未完成的半提交状态
- 任何需要多表强一致才能成立的聚合对象

换句话说，本批次中 `Redis` 的角色是：

- 共享运行态承载层
- 热点只读缓存层

而不是：

- 多实例强一致事务真相层

#### 6.7.5 推荐的 key 规范

建议统一使用 `collab:{domain}:{type}:{id}` 形式，避免后续键名失控。

第一批至少统一以下 key：

- `collab:doc:snapshot:{docId}`
- `collab:doc:meta:{docId}`
- `collab:user:docs:{userId}:{page}:{limit}`
- `collab:presence:{docId}`
- `collab:idempotency:{eventId}`
- `collab:runtime:room_socket:conn:{connectionId}`
- `collab:runtime:room_socket:doc:{docId}:connections`
- `collab:runtime:room_socket:doc:{docId}:client:{clientId}:connections`

#### 6.7.6 TTL 建议

第一批建议直接把 TTL 规则写进配置层，避免散落在业务代码里：

- 文档快照缓存：`5-30 min`
- 文档元信息缓存：`10-30 min`
- 用户文档列表缓存：`1-5 min`
- presence 结果缓存：`3-10 s`
- 幂等键：`10-60 min`
- 运行态索引：
  - 以显式增删为主
  - TTL 仅作为异常退出后的兜底

#### 6.7.7 每条链路的失效规则

为了避免缓存和真相脱节，第一批统一采用“`MySQL` 成功提交后删缓存，TTL 兜底”的策略。

- `GET /docs/:docId`
  - 读：先查 `collab:doc:snapshot:{docId}`
  - miss：回源 `MySQL`
  - 回填：把最新快照写回 `Redis`
- `POST /docs`
  - 成功后：
    - 删除创建者相关文档列表缓存
    - 写入或删除新文档对应的 `meta/snapshot` 缓存
- `set_cell`
  - 成功后：
    - 删除 `collab:doc:snapshot:{docId}`
    - 删除 `collab:doc:meta:{docId}`
- `set_title`
  - 成功后：
    - 删除 `collab:doc:meta:{docId}`
    - 删除 `collab:doc:snapshot:{docId}`
    - 删除相关用户列表缓存
- `import_sheet`
  - 成功后：
    - 删除 `collab:doc:snapshot:{docId}`
    - 删除 `collab:doc:meta:{docId}`
    - 删除相关用户列表缓存
- `undo`
  - 成功后：
    - 删除 `collab:doc:snapshot:{docId}`
    - 删除 `collab:doc:meta:{docId}`
  - 不需要删除 `undo/redo` Redis key，因为本批次不缓存 `user_op_state`
- `redo`
  - 成功后：
    - 删除 `collab:doc:snapshot:{docId}`
    - 删除 `collab:doc:meta:{docId}`
  - 同样不缓存 `user_op_state`
- `join`
  - 更新运行态索引
  - 如果做了 presence 结果缓存，则删除 `collab:presence:{docId}`
- `leave`
  - 更新运行态索引
  - fully-offline 后删除 `collab:presence:{docId}`
- `presence`
  - 第一优先级建议：基于运行态索引即时组装
  - 如果缓存 presence 结果，只允许极短 TTL，并在 `join/leave/disconnect/switch-room` 后删除
- `GET /docs?userId=...`
  - 读：先查列表缓存，miss 回源 `MySQL`
  - 失效：
    - `POST /docs`
    - 文档标题变化
    - 参与关系变化
    - import 导致文档元信息明显变化

#### 6.7.8 本批次需要改造的代码层

第一批如果要一次性做完基础改造，至少要覆盖以下层次：

- `config`
  - 新增 Redis 缓存 TTL、开关和 key 前缀配置
- `infra/redis`

  - 为 `doc snapshot`、`doc meta`、`user docs list` 增加缓存模块

  - 为读路径接入 cache-aside
  - 为写路径接入写后失效
- `room/runtime`
  - 持续保持在线运行态与 presence 索引一致
- `tests`
  - 增加命中、失效、回源、多实例一致性测试
- `docs`
  - 补充 key 规范、TTL 规范和链路失效说明

#### 6.7.9 本批次必须补的测试

缓存改造不能只改代码不补验证，至少应补以下测试：

- `doc snapshot`
  - 首次读取 miss 回源成功
  - 第二次读取命中缓存
  - `set_cell/set_title/import_sheet/undo/redo` 后缓存失效
- `user docs list`
  - 列表首次读取 miss 回源

  - `join/leave` 后 presence 结果不读到旧值
  - 多实例下 presence 结果保持一致
- 兼容性
  - `memory` 模式不被破坏
  - `mysql` 模式不被破坏
  - `mysql + redis(runtime) + redis(broadcast)` 模式不被破坏

#### 6.7.10 本批次完成标准

第一批缓存改造完成后，至少应满足：

- `GET /docs/:docId` 已具备稳定的 Redis 缓存与回源能力
- 文档写入后不会继续读到旧快照
- 用户文档列表具备可控缓存与明确失效
- presence 不因缓存引入明显不一致
- `undo/redo` 权威状态仍然由 `MySQL user_op_state` 维护
- 当前已有 `memory/mysql/redis` 主链路测试继续通过

#### 6.7.11 本批次推荐实施顺序

如果你打算一次改完基础部分，建议按以下顺序落地：

1. 先补配置层、key 规范、Redis cache helper
2. 再接入 `doc snapshot` 缓存
3. 再接入 `doc meta` 和 `user docs list` 缓存
4. 再梳理 presence 是否只做即时组装还是极短 TTL 结果缓存
5. 最后补测试、补文档、跑全链路回归

#### 6.7.12 当前落地结论

结合当前代码和回归结果，本批次目标已经基本完成：

- `GET /docs/:docId` 已具备 `Redis` 缓存与回源能力
- `GET /docs` 已具备用户列表缓存与失效能力
- `set_cell`、`set_title`、`import_sheet`、`undo`、`redo` 已接入写后失效
- `memory + memory`、`mysql + memory`、`mysql + redis` 三条主链路都已补过验证
- `Redis` 继续只承接共享运行态与热点缓存，不作为事务真相层

当前未纳入本批次范围的仍包括：

- 应用本地内存一级缓存
- 更重的缓存容量治理与命中率优化
- 基于广播或版本号的本地缓存失效通知

## 7. 改造点三：优化 seq 后写方案，评估消息队列 / OT / CRDT

### 7.1 改造目标

让当前的全局 `seq` 和后写覆盖策略在分布式环境下仍然成立，并在此基础上评估是否需要引入更复杂的协同算法。

### 7.2 当前问题

当前一期中的 `currentSeq` 递增和快照更新建立在单机内存假设上，到了多实例环境会出现：

- 不同实例基于各自旧状态同时分配相同 `seq`
- 不同实例对“谁是后写”理解不一致
- `undo/redo` 所依赖的用户状态无法跨实例共享
- 广播和状态落地之间缺少统一顺序来源

### 7.3 建议的优先方案

二期建议优先采用以下工程化方案：

- 保留文档级全局 `seq`
- 保留 append-only `history`
- 保留每用户每文档的 `undo/redo` 状态
- 通过共享状态和原子分配来保证顺序一致

在这个阶段，更推荐的手段是：

- `MySQL` 事务 + 版本校验
- 文档级分布式锁
- 单文档串行执行
- 按 `docId` 做粘性路由

当前这一阶段实际上已经选择并落地的路径是：

- 以 `MySQL` 事务和 `SELECT ... FOR UPDATE` 收口文档真相写入
- 以文档级分布式锁扩大关键写路径的跨实例临界区
- 继续保留文档级全局 `seq`
- 继续保留 append-only `history`
- 通过 `history.base_seq`、`baseSeq`、`sourceSeq` 和 barrier 检查实现最小服务端 `OT / rebase`

当前并没有采用 `Redis INCR` 作为 `seq` 真相来源；`seq` 仍然以文档权威状态提交结果为准。

### 7.4 关于消息队列

消息队列适合做以下事情：

- 异步削峰
- 广播解耦
- 审计异步写入
- 历史事件回放

消息队列不天然解决以下问题：

- 同一文档的全局顺序定义
- 同一次业务提交的强一致事务
- 并发写入冲突的最终裁决

因此，消息队列更适合作为“辅助分发和解耦组件”，而不是直接替代一致性方案本身。

### 7.5 关于 OT / CRDT

在当前表格协同场景下，二期不建议默认将 `OT/CRDT` 作为必做项。

原因如下：

- 当前主要操作粒度是 `cell` 级，而不是富文本逐字符编辑
- 当前更大的问题是共享状态和顺序一致性，而不是复杂编辑意图合并
- `OT/CRDT` 设计、调试和验证成本高，适合在更复杂协同需求明确后再引入

可以先采用以下策略：

- 不同用户修改不同单元格时允许并发写入
- 同一单元格冲突时采用明确的工程策略，例如版本校验失败重试或后写覆盖
- 所有成功操作都进入 `history`

当前已经落地的最小方案不是完整 `CRDT`，也不是富文本级复杂 `OT`，而是“服务端中心化最小 `OT / rebase`”：

- `set_cell` 支持可选 `baseSeq`
- `set_title` 支持可选 `baseSeq`
- `history` 已增加 `base_seq`
- `undo/redo` 已改为基于 `sourceSeq` 与后续 history 做服务端重放
- `import_sheet` 已作为 barrier 生效，跨 barrier 的 stale 请求会返回 `4090`

因此，改造点三当前可以视为“最小顺序治理已落地并通过核心测试”，但还不能表述为“完整 OT 引擎已完成”。

### 7.6 需要注意的地方

- 不要把“引入消息队列”和“已经解决一致性”画等号
- 不要把“引入分布式锁”和“已经实现 OT/CRDT”画等号
- 必须先定义全局顺序的来源，再讨论后写策略是否成立
- `undo/redo` 依赖的不只是历史，还依赖用户私有操作栈，因此不能只解决 `history`，不解决 `user_op_state`
- 如果二期仍沿用后写覆盖，就要在设计文档中明确说明这是一种业务策略，而不是算法缺陷

### 7.7 阶段完成标准

- 多实例下 `seq` 单调递增仍成立
- 同一文档的写入顺序有统一定义
- `undo/redo` 在多实例下仍可正确执行
- 广播顺序和落地顺序不出现明显冲突

## 8. 改造点四：升级为多实例形态

### 8.1 改造目标

让系统从单机内存协同服务升级为多实例可部署、可扩展、可恢复的分布式协同服务。

### 8.2 核心能力

多实例不是简单地把应用复制成多份，而是至少要补齐以下能力：

- 统一的状态存储
- 统一的顺序收口
- 跨实例广播
- 路由收敛
- 故障恢复

### 8.3 实施内容

- 为每个应用实例分配 `serverId`
- 连接元数据中增加 `serverId`、`connectionId` 等字段
- 接入网关或负载均衡，并按 `docId` 做粘性路由
- 使用 `Redis Pub/Sub` 或等价消息分发机制做跨实例广播
- 保证某个实例下线后，其运行态能从共享存储中恢复或重建

### 8.4 推荐方案

推荐采用以下思路：

- 同一文档请求尽量路由到同一实例
- 真正的业务状态统一落在 `MySQL`
- 热点运行态和跨实例协调交给 `Redis`
- 实例只保留短时本地缓存，不保留权威真相

### 8.5 需要注意的地方

- 如果没有跨实例广播，房间里的协同消息只能被本机连接看到
- 如果没有统一路由，同一文档在不同实例上同时写入会显著增加顺序和冲突处理难度
- 如果没有共享 `user_op_state`，用户在实例切换后会出现 `nothing to undo` 之类的问题
- 不要把多实例理解成单纯提升吞吐，它首先是部署形态升级，会引入一致性与观测性成本
- 必须补充日志追踪、链路标识、实例标识等排查手段，否则分布式问题很难定位

### 8.6 阶段完成标准

- 两个及以上实例可同时提供服务
- 同一文档的在线协同在多实例下仍能正常广播
- 用户切换实例后不会丢失权威文档状态和 `undo/redo` 状态
- 单实例故障不会导致所有文档状态不可恢复

### 8.7 当前完成情况

当前多实例形态已经完成第一阶段落地：

- 已接入 `serverId`
- 已实现跨实例广播骨架并覆盖关键协同消息
- 已补充多实例自动化测试
- 已覆盖跨实例 `presence` 查询与离线收敛
- 已覆盖同一 `clientId` 跨实例多连接的在线 / 离线判定
- 已覆盖 Redis 共享运行态、缓存失效、关键写路径锁和一部分跨实例 OT / rebase 场景

当前尚未完成的部分主要是：

- 网关层面的正式粘性路由
- 更完整的实例故障恢复治理
- 更系统化的链路追踪与观测能力

## 9. 改造点五：接入应用内存，形成三级缓存

### 9.1 改造目标

在 `MySQL + Redis` 共享状态稳定之后，引入应用本地内存缓存，形成 `应用内存 -> Redis -> MySQL` 的三级缓存架构，以降低热点读延迟和共享缓存压力。

### 9.2 建议缓存层级

- 一级缓存：应用内存
- 二级缓存：`Redis`
- 三级存储：`MySQL`

### 9.3 适合缓存的数据

优先缓存以下内容：

- 文档元信息
- 热点文档快照
- 热点在线用户列表
- 常用配置项和白名单数据

### 9.4 不建议优先缓存的数据

以下数据需要谨慎处理：

- 全量 `history`
- 高变更频率且强一致要求高的 `undo/redo` 状态
- 需要严格事务一致的提交中间态

### 9.5 实施内容

- 为热点读路径设计本地缓存
- 设计缓存更新和失效策略
- 建立统一缓存键规范
- 结合 `Redis` 订阅或版本号实现本地缓存失效通知
- 监控缓存命中率、回源比例和脏读风险

### 9.6 需要注意的地方

- 本地缓存只能是性能优化层，不能重新变成权威状态来源
- 如果没有跨实例失效通知，本地缓存很容易读到旧快照
- 三级缓存会增加排查难度，必须配合监控和日志
- 不要在状态真相尚未稳定时过早引入本地缓存，否则会掩盖一致性问题
- 缓存命中率不高的场景不值得过度复杂化，应优先缓存热点明确、收益稳定的数据

### 9.7 阶段完成标准

- 热点文档读取延迟明显下降
- `Redis` 访问压力得到分担
- 本地缓存不会导致明显的旧数据问题
- 缓存层故障时系统仍可回退到 `Redis/MySQL`

## 10. 二期阶段划分建议

为了降低风险，建议将二期拆成以下几个阶段：

### 10.1 阶段一：持久化收口

- 接入 `MySQL`

### 10.2 阶段二：共享运行态

- 未采用 `Redis` 原子计数器作为 `seq` 真相来源

### 10.3 阶段三：多实例协同

- 完成 `serverId`、`connectionId` 设计
- 完成跨实例广播
- 完成粘性路由和实例恢复机制

当前状态：

- `serverId`、`connectionId` 与跨实例广播已落地
- 粘性路由和实例恢复机制仍属于后续治理项

### 10.4 阶段四：一致性增强

- 优化 `seq` 分配
- 明确冲突处理策略

## 11. 二期重点风险

二期推进过程中，需要重点关注以下风险：

- 状态来源不唯一，导致一部分数据在 `MySQL`，另一部分仍在本地内存
- `seq` 与快照写入不同步，导致历史顺序和当前状态不一致
- 跨实例广播不完整，导致协同用户看到的状态不同
- `undo/redo` 栈共享不正确，导致多实例下撤销语义失效
- 过早引入消息队列、分布式锁、三级缓存，导致系统复杂度远超当前排查能力

## 11.1 当前验证口径

为了保证“迁移不破坏旧链路”，当前至少应持续验证以下测试口径：

- `memory` 单机：
  - `node --test tests/docs.test.js`
  - `node --test --test-concurrency=1 tests/ws.test.js`
- `mysql + memory` 持久化：
  - 在 PowerShell 中显式覆盖
    - `$env:STORE_DRIVER='mysql'`
    - `$env:CACHE_DRIVER='memory'`
    - `$env:RUNTIME_STATE_DRIVER='memory'`
    - `$env:COLLAB_BROADCAST_DRIVER='memory'`
    - `$env:IDEMPOTENCY_DRIVER='memory'`
    - `$env:DOC_LOCK_DRIVER='memory'`
  - `node --env-file=.env --test tests/docs.test.js`
  - `node --env-file=.env --test --test-concurrency=1 tests/ws.test.js`
- `mysql + redis` 多实例：
  - `npm run test:cache-redis`
  - `npm run test:multi-instance`

当前这套验证口径的目的不是追求“所有测试都只跑一次”，而是明确确认：

- `memory` 原链路未被破坏
- `mysql + memory` 持久化链路正常

- 多实例 `presence` 与 fully-offline 行为正常
- 最小服务端 `OT / rebase` 在单机与 `Redis` 链路下都具备回归覆盖

需要注意的是：

- 不建议直接用本地 `.env` 的全分布式配置去跑 `ws.test.js` 全量，因为其中一部分用例是单实例语义断言
- `ws.test.js` 更适合作为 `memory` 或 `mysql + memory` 口径验证

## 12. 结论

二期优化的核心方向不是简单地把更多组件堆进系统，而是完成以下转变：

- 从单机内存真相，转向共享持久化真相
- 从本地运行态，转向多实例共享运行态
- 从单机顺序假设，转向分布式顺序收敛
- 从单层缓存，转向受控的三级缓存

因此，二期更推荐的落地路线是：

- 先 `MySQL`
- 再 `Redis`
- 再多实例广播与路由
- 再优化 `seq` 和冲突策略
- 最后再做三级缓存和更高阶协同算法评估

如果二期按这个顺序推进，可以最大程度复用当前一期已经完成的业务流程，同时把系统逐步演进为可持久化、可扩展、可恢复的协同后端。
