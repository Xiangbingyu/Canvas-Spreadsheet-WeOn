# 协同实时态优化方案

## 1. 文档目标

本文档用于整理当前 `backend-js` 协同写入链路的整体优化思路，重点说明以下内容：

- 为什么当前“同步写最终状态”方案会限制吞吐量
- 为什么应将“操作排序确认”和“最终持久化物化”拆开
- 为什么建议由 `Redis` 承担实时协同状态，而由 `MySQL` 承担异步持久化
- 当前代码中需要改动的模块、职责和数据流
- 改造后系统的权威状态边界、失败恢复方式与验收标准

本文档不讨论前端 `pending-op transform` 或 `local-first` 交互改造，仅聚焦后端整体写入架构优化。

## 2. 当前实现现状

当前后端已经具备以下能力：

- `set_cell`、`set_title` 支持基于 `baseSeq` 的最小服务端 `rebase`
- `undo/redo` 支持基于 `sourceSeq` 的重放语义
- `import_sheet` 已作为 `OT barrier`
- 核心业务状态已支持 `MySQL`
- 跨实例广播、共享运行态、分布式锁、缓存已支持 `Redis`

当前主链路的典型写入路径大致如下：

1. 进入文档级锁
2. 读取当前文档状态
3. 基于当前状态和 `baseSeq/sourceSeq` 做检查、重排序和冲突判断
4. 直接更新最终文档状态
5. 同步写入 `history`
6. 同步更新 `user_op_state`
7. 释放文档锁
8. 再做缓存失效、审计记录与广播

这一方案的优点是实现简单、一致性边界清晰，但也带来几个明显问题：

- 每次高频编辑都要同步碰 `MySQL`
- 热文档会频繁更新最终状态，写放大较大
- 同一文档所有写请求都必须等待 SQL 主链路完成
- 实时协同确认点和持久化物化点耦合过紧
- 未来若继续增强实时协同体验，后端主链路会成为瓶颈

## 3. 当前瓶颈判断

当前系统的主要瓶颈并不在于：

- 没有 `seq`
- 没有 `baseSeq`
- 没有 `rebase`
- 没有共享状态

真正的瓶颈在于：

- 实时确认路径仍然依赖同步 SQL 更新
- “操作确认”和“最终状态持久化”是同一件事
- `MySQL` 同时承担了在线协同确认和长期存储两个角色

因此，继续优化当前架构的关键，不是再讨论是否要不要 `OT`，而是要把：

- 在线协同主路径
- 长期持久化路径

从同一条同步流程中拆开。

## 4. 总体优化思路

整体优化方向为：

- `Redis` 承担在线实时状态与短期操作流
- `MySQL` 承担异步持久化、快照归档与恢复
- 同一文档写操作先在 `Redis` 中完成顺序确认，再立即广播
- 后台 worker 再把已确认操作异步落到 `MySQL`
- 最终快照不再要求每次操作都同步改写，而由后台按操作流异步物化

简化表述如下：

- 在线写 `Redis`
- 异步沉淀 `MySQL`
- 同步确认操作
- 异步生成状态

这意味着系统要从“状态优先”改为“操作优先”：

- 当前方案：先改最终状态，再把它视为真相
- 优化方案：先确认操作，最终状态由操作折叠生成

## 5. 目标架构

### 5.1 核心原则

- 同一文档内仍然需要统一顺序
- 协同语义继续沿用当前 `seq + baseSeq/sourceSeq + rebase + barrier`
- 在线确认必须尽量轻，不依赖同步 SQL
- 异步物化不得反向影响已确认操作的在线可见性
- 恢复路径必须能从持久化快照和操作日志重建文档状态

### 5.2 真相分层

改造后，系统中的“真相”不再只有一层，而是分成两层：

- **实时真相层**：`Redis`
- **长期持久化层**：`MySQL`

两层职责如下：

- `Redis` 保存最新在线状态、当前 `seq`、短期 `op_log`、运行态索引、`undo/redo` 栈等实时协同信息
- `MySQL` 保存长期 `op_log/history`、稳定快照、checkpoint、文档元数据、审计归档

### 5.3 目标写入链路

任意一个写操作，例如 `set_cell`，目标链路如下：

1. 客户端发起写请求
2. 服务端进入同一文档的顺序确认点
3. 读取 `Redis` 当前文档状态和当前 `seq`
4. 基于 `baseSeq/sourceSeq` 做检查、重排序和冲突判断
5. 生成新的全局 `seq`
6. 将该操作同步写入 `Redis` 实时操作流，并更新 `Redis` 当前在线状态
7. `Redis` 写成功后，立即视为本次操作已确认
8. 立即回复发送方并向房间广播该已确认操作
9. 后台 worker 异步将该操作顺序写入 `MySQL`
10. 后台按策略生成新的 snapshot/checkpoint

这个模型下：

- 主链路确认点在 `Redis`
- `MySQL` 不再位于用户等待路径中
- 广播基于已确认的操作，而不是基于已落库的最终状态

## 6. 为什么要拆分“排序”和“写入”

当前系统中，“排序”和“写入”被放在一起处理：

- 先拿文档锁
- 再排序/rebase
- 再直接更新最终状态

这种方式的问题在于：

- 排序是实时协同必须的
- 最终快照写入不是每次都必须同步完成的

将两者拆开后：

- 排序只负责确定一条操作的在线生效顺序
- 持久化只负责保证该顺序最终可恢复

换句话说：

- **在线确认** 应追求轻量、稳定、低延迟
- **长期物化** 应追求可恢复、可重建、可批处理

这就是本次优化的核心逻辑。

## 7. Redis 实时态设计

### 7.1 Redis 承担的职责

`Redis` 不再只是缓存，而是承担实时协同层职责，建议承接以下内容：

- 每个文档当前 `currentSeq`
- 每个文档当前在线快照或在线可写状态
- 每个文档最近一段时间的 `op_log`
- `undoStack/redoStack`
- `import_sheet` barrier 相关信息
- 房间在线成员与运行态元数据
- worker 的消费进度与 checkpoint 推进信息

### 7.2 Redis 中推荐维护的数据

建议按文档维护如下结构：

- `doc:{docId}:state`
- `doc:{docId}:seq`
- `doc:{docId}:ops`
- `doc:{docId}:user-op:{clientId}`
- `doc:{docId}:barrier`
- `doc:{docId}:checkpoint`

其中：

- `state` 表示当前在线状态
- `seq` 表示当前文档最新全局版本号
- `ops` 表示最近一段增量操作流
- `user-op` 表示当前用户的 `undo/redo` 栈
- `barrier` 记录最近一次 `import_sheet` 的关键版本
- `checkpoint` 表示最近已物化到 `MySQL` 的稳定位置

### 7.3 Redis 中的操作流

建议使用以下任一种方式承载短期 `op_log`：

- `Redis Stream`
- `List + seq`
- `Hash/JSON + Stream`

推荐优先考虑 `Redis Stream`，原因如下：

- 更适合做顺序追加
- 更适合 worker 消费
- 更适合保留消费位点
- 比纯内存结构更容易做持久化和恢复

## 8. MySQL 持久化设计

### 8.1 MySQL 承担的职责

`MySQL` 在优化后不再负责在线确认，而主要承担：

- 长期 `op_log/history` 存储
- 文档稳定 snapshot/checkpoint 存储
- 基础文档元数据存储
- 审计日志归档
- 故障恢复和离线查询

### 8.2 建议保留或新增的数据结构

建议重点维护以下结构：

- `doc`
- `history` 或新的 `op_log`
- `snapshot_checkpoint`
- `audit_log`

其中：

- `doc` 只保存文档元信息和最近稳定 checkpoint 信息
- `history/op_log` 保存按 `docId + seq` 递增的正式操作日志
- `snapshot_checkpoint` 保存某个 `seq` 下的稳定快照
- `audit_log` 保存业务审计信息

### 8.3 MySQL 的角色调整

当前 `MySQL` 既保存状态，又参与实时写入确认。

优化后应调整为：

- 在线链路不依赖它确认操作
- 它只负责在后台把实时状态沉淀成长期可恢复状态

因此，`MySQL` 的关键目标变为：

- 可恢复
- 可回放
- 可归档

而不是：

- 每次操作都必须同步更新到最新

## 9. 在线写请求详细流程

### 9.1 `set_cell`

`set_cell` 的目标处理流程如下：

1. 请求进入 `ws/handlers/setCell.js`
2. 由 `service/cellService.js` 承担主流程
3. 在文档顺序确认点中读取 `Redis` 当前状态
4. 执行当前已有的 `baseSeq` 校验和最小 `rebase`
5. 若冲突则返回 `4090`
6. 若可继续执行，则分配新的 `seq`
7. 将该操作追加到 `Redis` `op_log`
8. 同步更新 `Redis` 当前文档在线状态
9. 同步更新 `Redis` 中对应用户的 `undoStack/redoStack`
10. 立即返回 `cell_updated`
11. 立即广播该已确认操作
12. 后台异步写入 `MySQL history/op_log`
13. 后台按策略更新快照

### 9.2 `set_title`

处理方式与 `set_cell` 对称：

- 排序点仍在服务端
- `baseSeq` 仍参与版本判断
- 在线状态写入 `Redis`
- 仅把正式操作异步沉淀到 `MySQL`

### 9.3 `undo/redo`

处理方式保持当前语义：

- 仍基于 `user_op_state`
- 仍基于 `sourceSeq`
- 仍要检查 `import_sheet barrier`

区别只在于：

- `user_op_state` 的主更新从 `MySQL` 改到 `Redis`
- `MySQL` 只异步补写正式 `history/op_log`

### 9.4 `import_sheet`

`import_sheet` 的特殊点在于：

- 它会整体替换在线快照
- 它会清空当前用户 `undo/redo` 栈
- 它是后续 stale 请求的 barrier

因此在 `Redis` 在线态中必须显式推进：

- 当前快照
- 当前 `seq`
- 当前 barrier 位置
- 当前用户操作栈

## 10. 顺序确认点与锁模型

### 10.1 仍然需要顺序确认点

优化后仍然不能取消“同一文档的顺序确认点”，否则：

- `seq` 会乱
- `baseSeq` 无法判断
- stale 请求的重排序会失真
- `undo/redo` 和 `import_sheet barrier` 会失效

### 10.2 推荐的顺序确认方式

可选方式包括：

- 保留当前文档级分布式锁，但缩小锁范围
- 基于每文档队列做单线程处理
- 基于分片 leader / actor 模型做文档串行化

在当前项目基础上，最务实的做法是：

- 暂时保留现有文档级锁
- 但让锁只保护 `Redis` 中的排序确认逻辑

也就是说，锁内应只保留：

- 读取 `Redis` 当前状态
- 做 `baseSeq/sourceSeq` 检查和 `rebase`
- 分配新的 `seq`
- 更新 `Redis` 在线状态
- 追加 `Redis` 操作流

而不再让锁包住：

- `MySQL` 同步写入
- 审计记录
- 缓存失效
- snapshot 物化

## 11. 广播模型调整

### 11.1 广播对象

正常实时协同时，广播内容不应是整份快照，而应是本次已确认操作。

广播建议包含：

- `type`
- `docId`
- `clientId`
- `seq`
- 当前操作的业务载荷
- 必要时的 `baseSeq/sourceSeq` 结果信息

### 11.2 为什么不广播整份快照

因为广播整份快照会导致：

- 体积过大
- 高并发下网络浪费明显
- 客户端 diff 处理成本高
- 与操作流驱动模型不一致

因此：

- 正常协同时广播 op
- 新用户加入、重连或版本落后过大时再返回 snapshot

## 12. 异步持久化与快照物化

### 12.1 异步 worker 负责的事情

后台 worker 应至少负责：

- 从 `Redis` 顺序读取未持久化的操作
- 把这些操作幂等地写入 `MySQL history/op_log`
- 根据策略生成新的 snapshot/checkpoint
- 推进每个文档的持久化位点
- 清理已稳定落盘的旧增量操作
- 在需要时补写审计信息

### 12.2 物化策略

快照不需要每条 op 都生成，可以采用以下任一策略：

- 按固定操作数生成
- 按固定时间窗口生成
- 按文档变更量阈值生成

推荐实际落地时同时结合：

- 操作数阈值
- 时间窗口阈值

以避免高频文档和低频文档都走同一种极端策略。

### 12.3 新客户端恢复方式

新客户端加入或服务恢复时：

1. 读取最近稳定 snapshot/checkpoint
2. 回放 checkpoint 之后的正式操作日志
3. 若 `Redis` 中存在更新且可信的实时态，则以 `Redis` 为最新在线状态

这保证了：

- 即使 snapshot 不是最新的
- 只要后续 op 仍可回放
- 文档状态仍然能重建

## 13. 一致性边界与失败处理

### 13.1 操作成功的定义

一条操作成功的定义应为：

- 已在 `Redis` 中完成顺序确认
- 已写入 `Redis` 实时态和短期操作流

也就是说：

- `Redis` 写成功后可立即视为本次操作在线生效
- `MySQL` 落盘不是在线成功的前置条件

### 13.2 失败处理原则

建议采用如下原则：

- `Redis` 写失败：本次请求失败，不广播
- `Redis` 成功但 `MySQL` 异步落盘失败：本次操作仍然在线有效，由 worker 重试
- worker 重复消费：通过 `docId + seq` 唯一约束保证幂等
- `Redis` 故障：通过 `MySQL snapshot + history/op_log` 恢复
- `import_sheet` 相关冲突：继续按当前 barrier 语义处理

### 13.3 可靠性要求

因为 `Redis` 在该方案中承担在线真相层职责，所以：

- 不能再把它只当普通缓存
- 需要开启持久化
- 需要设计恢复方案
- 需要保证 worker 消费的幂等和重试

## 14. 当前代码中需要修改的地方

以下内容应作为本次架构优化的主要改造面。

### 14.1 `service` 层

需要重点改造：

- `service/cellService.js`
- `service/titleService.js`
- `service/undoRedoService.js`
- `service/importService.js`

改造方向：

- 主流程从“同步写 `MySQL` 当前状态”改为“同步写 `Redis` 在线状态”
- 保留当前 `rebase`、`barrier`、`undo/redo` 语义
- 将 `MySQL` 写入改为异步沉淀

### 14.2 `store` 层

当前核心存储主要集中在：

- `store/docStore.js`
- `store/mysql/*`
- `store/memory/*`

改造方向：

- 新增面向 `Redis` 的实时态 `store`
- 将 `doc.currentSeq`、当前在线 snapshot、用户操作栈、短期 `op_log` 迁到 `Redis`
- 将 `MySQL` 侧 `store` 调整为偏长期持久化能力

### 14.3 `infra/redis`

当前已存在：

- `infra/redis/client.js`
- `infra/redis/pubsub.js`
- `infra/redis/lock.js`

需要新增：

- 文档实时状态访问封装
- 文档操作流访问封装
- worker 消费位点管理
- checkpoint 位点管理

### 14.4 `ws` 层

需要重点改造：

- `ws/handlers/setCell.js`
- `ws/handlers/setTitle.js`
- `ws/handlers/undo.js`
- `ws/handlers/redo.js`
- `ws/handlers/importSheet.js`

改造方向：

- 回复与广播依据从“同步 SQL 成功”切换为“Redis 实时态确认成功”
- 广播内容进一步向“已确认操作”靠拢
- 避免继续强化“同步写最终状态”的语义依赖

### 14.5 异步 worker

建议新增后台模块，例如：

- `worker/opLogFlushWorker.js`
- `worker/snapshotMaterializeWorker.js`

职责包括：

- 从 `Redis` 拉取未持久化 op
- 顺序写入 `MySQL`
- 生成快照
- 推进 checkpoint
- 清理过期增量日志

### 14.6 审计和缓存

当前：

- 审计与缓存逻辑已基本在锁外

优化后建议：

- 审计改为消费已确认 op 后异步补写
- 快照缓存由 checkpoint 推进时刷新
- 避免写请求后立即做粗粒度缓存失效

## 15. 建议保留不动的部分

以下逻辑建议尽量保留：

- `seq` 的文档级全局版本语义
- `set_cell/set_title` 的 `baseSeq` 处理语义
- `undo/redo` 的 `sourceSeq` 语义
- `import_sheet` 作为 barrier 的规则
- 当前统一错误码和返回码体系
- 当前 `service` 层作为业务主层的分层结构

因为这些能力本身并不是当前瓶颈，相反，它们是本次架构升级后仍应复用的协同语义基础。

## 16. 风险与注意事项

本方案最大的变化，不是 `Redis` 用得更多，而是：

- `Redis` 从“缓存/共享运行态”升级为“在线真相层的一部分”

因此要特别注意：

- 不能把纯内存结构当作权威 `op_log`
- 若使用 `Redis` 承担在线确认，必须配套持久化和恢复策略
- worker 必须幂等
- `Redis` 与 `MySQL` 之间的位点关系必须可追踪
- 新客户端恢复路径必须清晰
- 旧逻辑不能出现“在线确认成功但系统无法恢复”的状态

换句话说，本方案提升吞吐量的代价，是提高了系统的“分层真相管理”复杂度。

## 17. 方案收益

完成该优化后，系统会获得以下收益：

- 在线主链路不再被同步 SQL 写入卡住
- 同一文档写请求的锁持有时间显著缩短
- 热文档高频编辑吞吐量提升
- 广播延迟下降，更适合实时协同
- 最终状态物化改为异步，便于做批处理和 checkpoint
- 后续若接入更完整的前端 local-first 机制，后端基础更契合

## 18. 验收标准

若本方案完成，后端应至少达到以下状态：

- 写请求主链路不再同步写 `MySQL` 最终状态
- 同一文档在线写入确认基于 `Redis` 实时态完成
- 已确认操作可立即广播，不依赖同步 SQL 落盘
- 后台 worker 能将实时操作流稳定落到 `MySQL`
- 可从 `snapshot + op_log` 重建文档状态
- `set_cell`、`set_title`、`undo`、`redo`、`import_sheet` 现有协同语义保持不变

## 19. 结论

当前系统已经具备 `seq`、`baseSeq`、`rebase`、`undo/redo`、`import_sheet barrier` 等协同基础能力，因此本次优化不应再围绕“是否重新设计协同算法”展开，而应围绕“如何把实时确认从同步 SQL 主路径中剥离”展开。

最合理的方向是：

- 保留当前服务端协同语义
- 保留同一文档顺序确认点
- 将实时确认前移到 `Redis`
- 将长期持久化后移到 `MySQL`
- 将最终状态生成改为异步物化

简化总结如下：

- 当前方案：同步写最终状态
- 目标方案：同步确认操作，异步生成状态

这就是本次后端整体优化方案的核心。
