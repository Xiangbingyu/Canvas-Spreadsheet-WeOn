# 后端分层职责简述

## 1. 文档目标

本文档用于说明 `Canvas-Spreadsheet-WeOn` 当前后端各层的职责边界，先给出简短版定义，方便后续逐层细化。

当前一期的实际实施范围，另见：

- `backend-js/docs/一期实施规划.md`

当前后端采用以下轻量分层：

- `routes`
- `ws`
- `protocol`
- `service`
- `domain`
- `store`
- `security`
- `idempotency`
- `cache`
- `config`
- `audit`
- `utils`

## 2. 分层总原则

- `routes` 和 `ws` 只做接入层与 controller 层
- 核心业务逻辑统一收口到 `service`
- `domain` 负责领域模型定义
- `store` 负责数据访问与存储抽象
- `security`、`idempotency`、`cache`、`audit` 提供横切能力
- `config` 统一管理配置
- `utils` 只放通用工具，不放核心业务

## 2.1 当前一期实施约束

- 一期先完成核心协同闭环
- 一期先不实现 `audit`
- 一期先不实现 `undo`
- 一期先不实现 `redo`
- 一期要保留 `audit`、`undo/redo` 的文件位置和后续接入点
- 一期默认不主动抽取公共 helper
- 如果后续确实需要抽取，由用户明确提出后再进行整理

## 3. 各层职责与实现文件

### 3.1 `routes`

定位：

- HTTP controller 层

当前主要职责：

- 负责 `docs` 相关 HTTP 接口
- 保留 `health` 健康检查接口
- 接收请求参数
- 调用 `service`
- 返回统一 HTTP 响应

不负责：

- 直接写内存表或数据库
- 实现业务主逻辑
- 处理复杂协同逻辑

建议文件：

- `routes/docs.js`
- `routes/health.js`

文件说明：

- `docs.js` 负责 `POST /docs`
- `health.js` 负责 `GET /health`
- 两者都只做 controller，不放复杂业务逻辑

### 3.2 `ws`

定位：

- WebSocket controller 层

当前主要职责：

- 管理 WebSocket 连接入口
- 分发消息到对应 handler
- 实现 `join`、`presence`、`set_cell`、`import_sheet`、`undo`、`redo`
- 负责回复当前连接和房间广播

不负责：

- 直接维护文档核心状态
- 直接实现 `undo/redo` 主逻辑

建议文件：

- `ws/index.js`
- `ws/dispatcher.js`
- `ws/handlers/join.js`
- `ws/handlers/presence.js`
- `ws/handlers/setCell.js`
- `ws/handlers/importSheet.js`
- `ws/handlers/undo.js`
- `ws/handlers/redo.js`

文件说明：

- `index.js` 负责 WebSocketServer 初始化
- `dispatcher.js` 负责按消息类型路由
- 各 `handler` 只负责参数接收、调用 `service`、回复和广播

### 3.3 `protocol`

定位：

- 协议定义层

当前主要职责：

- 定义 WebSocket 消息类型
- 定义错误码
- 定义统一响应结构
- 定义基础校验规则

目标：

- 避免在各层硬编码协议字段和消息常量

建议文件：

- `protocol/messageTypes.js`
- `protocol/errorCodes.js`
- `protocol/responseSchema.js`
- `protocol/validators.js`

文件说明：

- `messageTypes.js`：维护 WebSocket 消息类型常量
- `errorCodes.js`：维护统一业务错误码
- `responseSchema.js`：维护 HTTP / WS 统一响应结构
- `validators.js`：维护基础消息校验规则

### 3.4 `service`

定位：

- 业务逻辑主层

当前主要职责：

- 创建文档
- 文档状态读取
- 房间加入与退出
- 在线用户同步
- `set_cell` 主流程
- `import_sheet` 主流程
- `undo/redo` 主流程
- 审计日志主流程封装

说明：

- 这一层是后端核心
- 负责把 `store`、`security`、`idempotency`、`cache`、`audit` 串起来

建议文件：

- `service/docsService.js`
- `service/healthService.js`
- `service/roomService.js`
- `service/presenceService.js`
- `service/cellService.js`
- `service/importService.js`
- `service/undoRedoService.js`
- `service/collabService.js`
- `service/auditService.js`

文件职责建议：

- `docsService.js`：创建文档
- `healthService.js`：健康检查
- `roomService.js`：加入房间、退出房间
- `presenceService.js`：在线用户读取与广播
- `cellService.js`：`set_cell` 主流程
- `importService.js`：`import_sheet` 主流程
- `undoRedoService.js`：`undo`、`redo` 主流程
- `collabService.js`：协同公共逻辑，如 `seq` 分配、广播载荷拼装
- `auditService.js`：统一封装审计日志记录入口，供其他 service 调用

### 3.5 `domain`

定位：

- 领域模型层

当前主要职责：

- `domain/entities/` 只放和数据库表一一对应的模型
- `domain/valueObjects/` 只放不落库的辅助模型
- 定义 `doc`
- 定义 `history`
- 定义 `user_op_state`
- 定义 `room_user`
- 定义 `room_socket`
- 定义审计日志模型

说明：

- 这一层严格按真实数据库结构对标
- `Entity` 和数据库表保持一一对应
- 不直接落库的辅助结构统一放到 `valueObjects`

建议文件：

- `domain/entities/doc.js`
- `domain/entities/history.js`
- `domain/entities/userOpState.js`
- `domain/entities/roomUser.js`
- `domain/entities/roomSocket.js`
- `domain/entities/auditLog.js`
- `domain/valueObjects/cellPosition.js`
- `domain/valueObjects/cellValueChange.js`
- `domain/valueObjects/operationRef.js`

文件说明：

- `doc.js` 对标 `doc`
- `history.js` 对标 `history`
- `userOpState.js` 对标 `user_op_state`
- `roomUser.js` 对标 `room_user`
- `roomSocket.js` 对标 `room_socket`
- `auditLog.js` 对标 `audit_log`
- `Value Object` 放在 `domain/valueObjects`

### 3.6 `store`

定位：

- 数据访问层

当前主要职责：

- 维护 `doc` 数据
- 维护 `history` 数据
- 维护 `user_op_state` 数据
- 维护 `room_user` 数据
- 维护 `room_socket` 数据
- 视 `audit` 是否持久化决定是否补充 `audit_log` 数据访问

说明：

- 当前一期是内存实现
- 二期替换为数据库实现时，优先保持 `service` 不变，只替换 `store`
- `DAO` 归 `store`
- 不建议把 `DAO` 放到 `domain`

建议文件：

- `store/docStore.js`
- `store/historyStore.js`
- `store/userOpStateStore.js`
- `store/roomUserStore.js`
- `store/roomSocketStore.js`
- `store/auditLogStore.js`

一期内存实现：

- `store/memory/docMemoryStore.js`
- `store/memory/historyMemoryStore.js`
- `store/memory/userOpStateMemoryStore.js`
- `store/memory/roomUserMemoryStore.js`
- `store/memory/roomSocketMemoryStore.js`
- `store/memory/auditLogMemoryStore.js`

对标关系：

- `docStore` 对标 `doc`
- `historyStore` 对标 `history`
- `userOpStateStore` 对标 `user_op_state`
- `roomUserStore` 对标 `room_user`
- `roomSocketStore` 对标 `room_socket`
- `auditLogStore` 对标 `audit_log`

### 3.7 `security`

定位：

- 基础安全层

当前主要职责：

- HTTP 基础安全拦截
- WebSocket 消息基础校验
- 消息大小限制
- 类型白名单
- 基础限流

说明：

- 一期先做基础保护
- 暂不扩展成完整权限系统

建议文件：

- `security/httpGuard.js`
- `security/wsGuard.js`
- `security/rateLimit.js`
- `security/messageWhitelist.js`

覆盖内容：

- HTTP 基础安全拦截
- WebSocket 消息基础校验
- 消息大小限制
- 类型白名单
- 基础限流

### 3.8 `idempotency`

定位：

- 幂等控制层

当前主要职责：

- 对 `POST /docs` 做基础幂等控制
- 对 `join` 做重复请求保护
- 对 `import_sheet` 做重复提交保护

后续可扩展：

- `set_cell`
- `undo`
- `redo`

建议文件：

- `idempotency/eventIdStore.js`
- `idempotency/idempotencyService.js`
- `idempotency/idempotencyKeys.js`

覆盖范围：

- `POST /docs`
- `join`
- `import_sheet`

### 3.9 `cache`

定位：

- 缓存维护层

当前主要职责：

- 为 `memory/redis` 提供统一缓存抽象
- 维护文档快照缓存
- 维护文档轻量元信息缓存
- 维护用户文档列表缓存

说明：

- 默认仍保留 `memory` 缓存链路
- 二期通过驱动切换扩展到 `Redis` 共享缓存
- 权威真相仍以 `MySQL` 为主，缓存采用 cache-aside + 写后失效

建议文件：

- `cache/cacheStore.js`
- `cache/cacheKeys.js`
- `cache/docSnapshotCache.js`
- `cache/docMetaCache.js`
- `cache/userDocsListCache.js`
- `cache/index.js`

覆盖内容：

- 文档快照缓存
- 文档轻量元信息缓存
- 用户文档列表缓存
- 缓存驱动关闭与测试资源回收

### 3.11 `audit`

定位：

- 记录 `set_cell`、`import_sheet`

说明：

- 一期先保留统一记录入口
- 二期再考虑持久化或接入消息队列
- 如果后续 `audit` 需要真正落库，则在 `store` 中补 `auditLogStore`

建议文件：

- `audit/auditService.js`
- `audit/auditEventTypes.js`

记录范围：

- `POST /docs`
- `join`
- `leave`
- `presence`
- `set_cell`
- `import_sheet`
- `undo`
- `redo`

## 5. 关于 `store`、数据库对标和 `audit`

这里需要明确：

- `doc` 必须在 `store` 中有对应文件
- `history` 必须在 `store` 中有对应文件
- `user_op_state` 必须在 `store` 中有对应文件
- `room_user` 必须在 `store` 中有对应文件
- `room_socket` 必须在 `store` 中有对应文件
- `audit` 如果只做轻量日志入口，可以先只有 `auditService`
- `audit` 如果要按后续数据库结构对标，建议也在 `store` 中补 `auditLogStore`

也就是说，当前建议是：

- `doc` -> `docStore`
- `history` -> `historyStore`
- `user_op_state` -> `userOpStateStore`
- `room_user` -> `roomUserStore`
- `room_socket` -> `roomSocketStore`
- `audit_log` -> `auditLogStore`

这样后续从一期内存实现切到二期数据库实现时，结构会更完整，也更容易平滑替换。

## 6. 结论

当前这版细化后的分层方案满足以下目标：

- `routes` 和 `ws` 保持轻量 controller 风格
- 核心逻辑统一放在 `service`
- `domain` 和 `store` 职责分离
- `store` 直接对标数据库结构
- `audit`、`security`、`idempotency`、`cache`、`config` 都有明确落点

后续只需要基于这份文档继续细化每个文件的字段、接口和流程即可。
