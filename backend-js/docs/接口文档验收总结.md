## 3. 已验证通过的接口

### 3.1 HTTP

已验证通过：

- `GET /`
- `GET /health`
- `POST /docs`
- `GET /docs`
- `GET /docs/:docId`

已确认语义：

- `POST /docs` 支持 `eventId` 幂等
- `GET /docs` 支持 `pageSize` 与 `pagesize`
- `GET /docs` 的 `created` / `participated` / `all` 语义与文档一致
- `GET /docs` 结果按 `updatedAt` 倒序，时间相同按 `docId` 倒序
- `GET /docs/:docId` 先查缓存，未命中回源 store，再回填缓存

### 3.2 WebSocket

已验证通过：

- `join`
- `presence`
- `set_cell`
- `import_sheet`
- `undo`
- `redo`
- 非法 JSON / 非对象消息 / 不支持消息类型错误处理

## 4. 已确认的关键行为

### 4.1 join

- 成功后返回 `join_ack`
- 若该 `clientId` 首次上线，则广播 `presence`
- 同一连接、同一 `docId + clientId` 的并发重复 `join` 具备幂等
- join 提交后，即使在线用户查询、presence 广播或 audit 失败，也不会反向改成 error

### 4.2 presence

- 必须先 `join`
- 发送方收到 `reply + broadcast` 共 2 条 `presence`
- 房间内其他客户端各收到 1 条
- 会写 `presence` audit

### 4.3 set_cell

- 同一格连续写入时，后写覆盖前写
- `seq` 为全文档单调递增
- 先写底层文档状态，再返回 `cell_updated` 并广播
- 会写 `history`
- 会更新当前用户的 `undoStack`
- 会清空当前用户的 `redoStack`
- 会同步更新文档缓存
- 会写 `set_cell` audit

### 4.4 import_sheet

- 当前实现不再做幂等控制
- 每次请求都会执行写入
- 会返回最新完整 `snapshot`
- 会清空当前用户的 `undoStack` 与 `redoStack`
- 会写 `history`
- 会同步更新文档缓存
- 会写 `import_sheet` audit

### 4.5 undo / redo

- 发送方必须已 `join` 且 socket 当前身份必须与 `clientId` 一致
- `undo`：从 `undoStack` 弹出并压入 `redoStack`
- `redo`：从 `redoStack` 弹出并重新压入 `undoStack`
- `undo` / `redo` 都会分配新的全局 `seq`
- `history` 中会记录 `sourceSeq`
- 提交边界之后，若 history / user-op-state / audit / broadcast 失败，只记录内部错误，不补发 `500`

## 5. 本次补齐的实现能力

### 5.1 undo / redo 栈上限

当前已加入用户操作栈上限控制。

配置位置：

- `backend-js/config/collabConfig.js`

当前配置项：

- `USER_OP_STACK_LIMIT`

默认值：

- `100`

行为：

- `set_cell` 入 `undoStack` 时仅保留最近 N 条
- `undo` 压入 `redoStack` 时仅保留最近 N 条
- `redo` 回压 `undoStack` 时仅保留最近 N 条

### 5.2 缓存配置收口

缓存相关容量配置已统一收口到：

- `backend-js/config/cacheConfig.js`

当前配置项：

- `DOCS_CACHE_MAX_ENTRIES`
- `HISTORY_CACHE_MAX_ENTRIES`
- `USER_OP_STATE_CACHE_MAX_ENTRIES`

说明：

- 当前内存缓存已支持按容量淘汰旧项
- 现有 TTL 配置仍保留在 `cacheConfig.js`

### 5.3 userOpState 清理策略

当前 `userOpState` 已支持两层清理：

1. 即时清理

- 当 `docId + clientId` 进入 `fully offline` 状态时，立即清理对应的 `userOpState`
- 适用于浏览器 / 页面连接关闭
- 也适用于同一 socket 切文档 / 切身份导致旧房间完全离线

2. TTL 兜底清理

- 配置项：`USER_OP_STATE_TTL_MS`
- 默认值：`30 * 60 * 1000`
- 当前实现为惰性清理：在读取或写入 `userOpStateStore` 时触发过期回收

## 6. 需要知道的当前实现事实

以下内容不是验收失败项，但需要作为实现事实保留：

- `set_cell` 与 `import_sheet` 当前不要求发送方先 `join`
- 未加入房间的 socket 可以直接写入并收到自身成功响应
- 这些未 join 的写入不会广播给不在房间内的客户端
- `import_sheet` 已取消幂等控制，文档与代码已对齐
- `userOpState` 的 TTL 清理当前是惰性触发，不是后台定时任务

## 7. 后续建议

建议后续继续推进以下工作：

- 若后端将接入真实数据库 / Redis / 多实例部署，按 `docId` 引入应用层串行写入机制，保证顺序语义
- 将现有内存缓存的 TTL 从“仅配置存在”进一步升级为真实过期驱逐机制
- 继续同步维护 `backend-js/docs/curl手动检查清单.md` 等手工验证文档，避免协议更新后出现示例漂移
