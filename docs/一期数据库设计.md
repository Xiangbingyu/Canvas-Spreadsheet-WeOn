# 第一期数据库设计

## 1. 设计目标

第一期的核心目标仍然是打通“创建文档 -> 加入房间 -> 编辑 -> 导入 -> 广播”的最小闭环。

结合当前一期规划，数据存储分为两类：

- 运行态内存结构：用于支撑 WebSocket 协同和在线用户同步
- 二期数据库映射：用于为后续数据库存储预留统一模型

说明：

- 一期严格实现时只使用内存结构，不落任何数据库表
- `sheet_docs`、`sheet_doc_history` 在一期仅作为二期数据库映射概念存在
- 在线房间和 socket 连接属于运行态数据，不建议直接落 MySQL

## 2. 总体划分

本期需要关注的“表”或“表形结构”包括：

- `docs`
- `roomUsers`
- `roomSockets`
- `sheet_docs`
- `sheet_doc_history`

其中：

- `docs`、`roomUsers`、`roomSockets` 是一期实际运行使用的内存态结构
- `sheet_docs`、`sheet_doc_history` 是二期数据库映射名称，不是一期实际落地表

## 3. 内存态结构设计

### 3.1 `docs`

用途：

- 保存当前文档最新状态
- 为 `join` 直接返回当前 `snapshot`
- 为 `set_cell` / `import_sheet` 提供当前上下文

推荐结构：

```ts
type Cell = {
  value: string;
};

type SheetSnapshot = {
  cells: Record<string, Cell>;
  styles: Record<string, unknown>;
  rowCount: number;
  colCount: number;
};

type SnapshotHistoryEntry = {
  seq: number;
  snapshot: SheetSnapshot;
  createdAt: number;
  source: 'init' | 'set_cell' | 'import_sheet';
};

type SheetDoc = {
  docId: string;
  title: string;
  snapshot: SheetSnapshot;
  seq: number;
  createdAt: number;
  updatedAt: number;
  history: SnapshotHistoryEntry[];
};

const docs = new Map<string, SheetDoc>();
```

字段说明：

- `docId`：业务文档 ID，对外暴露给前后端
- `title`：文档标题，一期可默认 `Untitled`
- `snapshot`：当前整张表的最新状态
- `seq`：当前文档最新服务端序号
- `createdAt`：创建时间
- `updatedAt`：最近更新时间
- `history`：有限历史快照

### 3.2 `roomUsers`

用途：

- 维护某个文档房间当前在线用户
- 为 `presence` 广播提供数据来源

推荐结构：

```ts
type RoomUser = {
  clientId: string;
  name: string;
  color: string;
};

const roomUsers = new Map<string, Map<string, RoomUser>>();
```

结构说明：

- 第一层 key 是 `docId`
- 第二层 key 是 `clientId`
- value 是 `RoomUser`

示意：

```ts
roomUsers = {
  doc_001: {
    client_001: { clientId: 'client_001', name: '用户001', color: '#3b82f6' },
    client_002: { clientId: 'client_002', name: '用户002', color: '#10b981' },
  },
};
```

### 3.3 `roomSockets`

用途：

- 保存某个房间当前的连接集合
- 用于向房间广播 `join_ack`、`presence`、`cell_updated`、`sheet_imported`

推荐结构：

```ts
const roomSockets = new Map<string, Set<WebSocket>>();
```

补充建议：

- 可以额外维护一个 `socketContext`
- 用于连接关闭时快速反查所属 `docId` 和 `clientId`

```ts
const socketContext = new Map<WebSocket, { docId: string; clientId: string }>();
```

说明：

- `roomUsers` 和 `roomSockets` 都是运行态数据
- 它们不建议存入 MySQL
- 如果后续要支持多实例部署，更适合演进为 Redis

## 4. 二期数据库映射

### 4.1 `sheet_docs`

一期含义：

- 不在第一期实际创建
- 用于表示未来数据库中“文档当前状态表”的映射目标

二期用途：

- 保存文档当前状态
- 用于替代内存中的 `docs` 当前态部分
- 在用户 `join` 时可直接读取当前最新快照

建议字段：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 数据库主键 |
| `doc_id` | `VARCHAR(64)` | 业务文档 ID |
| `title` | `VARCHAR(255)` | 文档标题 |
| `seq` | `BIGINT UNSIGNED` | 当前最新序号 |
| `snapshot_json` | `JSON` | 当前整张表快照 |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |

设计理由：

- `doc_id` 作为业务唯一键，前后端都围绕它通信
- `seq` 放在当前文档表中，`join` 时可直接返回
- `snapshot_json` 直接存整表快照，符合一期最小闭环设计
- 一期不拆 `sheet_cells` 等细粒度表，避免设计过重

建议映射字段：

- `id`
- `doc_id`
- `title`
- `seq`
- `snapshot_json`
- `created_at`
- `updated_at`

### 4.2 `sheet_doc_history`

一期含义：

- 不在第一期实际创建
- 用于表示未来数据库中“文档历史快照表”的映射目标

二期用途：

- 保存文档历史快照
- 为后续 `undo/redo`、调试和版本回溯预留数据

建议字段：

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT UNSIGNED` | 数据库主键 |
| `doc_id` | `VARCHAR(64)` | 业务文档 ID |
| `seq` | `BIGINT UNSIGNED` | 该历史快照对应的服务端序号 |
| `source` | `VARCHAR(32)` | 来源：`init` / `set_cell` / `import_sheet` |
| `snapshot_json` | `JSON` | 历史快照 |
| `created_at` | `DATETIME` | 创建时间 |

设计理由：

- `(doc_id, seq)` 唯一约束，保证一个文档每个序号只有一条历史
- `source` 有助于区分历史来源
- `snapshot_json` 直接保存完整快照，最贴近一期设计文档

建议映射字段：

- `id`
- `doc_id`
- `seq`
- `source`
- `snapshot_json`
- `created_at`

## 5. 对应关系

运行态和持久化之间的对应关系如下：

- 一期内存中的 `docs[docId]` 可映射为二期数据库中的 `sheet_docs` 一行当前状态
- 一期内存中的 `docs[docId].history[]` 可映射为二期数据库中的 `sheet_doc_history` 多行历史记录
- `roomUsers` 仅作为在线状态，不对应 MySQL 表
- `roomSockets` 仅作为广播连接集合，不对应 MySQL 表

## 6. 建议的仓储接口

为了让内存版和数据库版可以平滑切换，建议统一收敛到相同的方法签名。

推荐接口：

```ts
type DocsStore = {
  createDoc(): Promise<{ docId: string }>;
  getDocState(docId: string): Promise<SheetDoc | null>;
  applySetCell(command: {
    docId: string;
    clientId: string;
    row: number;
    col: number;
    value: string;
  }): Promise<{
    docId: string;
    seq: number;
    clientId: string;
    row: number;
    col: number;
    value: string;
  } | null>;
  applyImportSheet(command: {
    docId: string;
    clientId: string;
    snapshot: SheetSnapshot;
  }): Promise<{
    docId: string;
    seq: number;
    clientId: string;
    snapshot: SheetSnapshot;
  } | null>;
};
```

## 7. 一期落地建议

建议按下面的顺序落地：

1. 一期实际运行仍以 `docs`、`roomUsers`、`roomSockets` 为主
2. `sheet_docs`、`sheet_doc_history` 在一期只作为二期映射概念保留
3. 持久化切换时，优先替换 `docs` 对应的仓储实现
4. `roomUsers`、`roomSockets` 暂不落数据库，后续如需多实例再引入 Redis

## 8. 当前结论

从一期范围出发，这版设计的关键点是：

- 主链路继续使用轻量内存结构保证开发效率
- 一期不创建数据库表，只保留文档当前态和历史快照的二期映射概念
- 在线用户和 socket 连接保持运行态管理
- 后续可以平滑从 `memory` 仓储切换到数据库仓储

## 9. 推荐文件映射

为了让“运行时结构”和“二期数据库映射”在代码层面更直观，建议采用如下映射：

- 一期运行时
  - `docs` -> `backend-js/store/memory/docsMemoryStore.js`
  - `roomUsers` -> `backend-js/store/memory/roomUsersMemoryStore.js`
  - `roomSockets` -> `backend-js/store/memory/roomSocketsMemoryStore.js`
- 一期顶层 store 出口
  - `docs` -> `backend-js/store/docsStore.js`
  - `roomUsers` -> `backend-js/store/roomUsersStore.js`
  - `roomSockets` -> `backend-js/store/roomSocketsStore.js`
- 二期数据库映射
  - `sheet_docs` <- `docs`
  - `sheet_doc_history` <- `docs.history`
