# 第一期功能清单

## 1. 目标

第一期目标是交付一个可演示的最小闭环版本，优先打通以下链路：

1. 用户进入系统并获得临时身份
2. 用户可以创建表格并进入表格页面
3. 用户可以通过分享链接打开同一张表格
4. 用户可以导入 Excel 数据到当前表格
5. 用户可以查看并修改表格内容
6. 多个用户可以通过 WebSocket 实时看到彼此的修改

本期重点是先完成业务闭环，不追求完整 Excel 能力，不实现复杂权限，不实现 undo/redo。

## 2. 范围定义

### 2.1 本期包含

- 临时身份
- 表格创建
- 表格分享
- 表格查看
- 单元格编辑
- Excel 导入
- WebSocket 实时同步
- 在线用户展示
- 基础健康检查接口

## 3. 用户故事

### 3.1 临时用户进入系统

- 用户首次进入前端时，系统自动生成一个临时身份
- 临时身份包含 `clientId`、昵称、展示颜色
- 临时身份保存在 `sessionStorage`
- 这里的“标签页”指浏览器标签页或浏览器窗口
- 在同一个标签页内从首页跳转到表格编辑页时，身份不会失效
- 关闭当前浏览器标签页或窗口后，身份失效

### 3.2 创建表格

- 用户可以在首页点击“创建表格”
- 系统创建一个新的空白表格文档
- 创建成功后自动跳转到表格详情页

### 3.3 分享表格

- 用户在表格页可以点击“分享”
- 系统复制当前表格链接
- 其他用户通过该链接可以进入同一张表格
- 一期默认拿到链接即可进入并编辑，不做权限区分

### 3.4 查看与编辑表格

- 用户进入表格页后，通过 WebSocket 加入对应房间
- 服务端返回当前文档快照
- 用户可以点击单元格并修改文本内容
- 修改提交后，本地立即更新，并同步给房间内其他用户

### 3.5 导入 Excel

- 用户可选择本地 `.xlsx` 文件
- 前端使用 `SheetJS (xlsx)` 解析第一个工作表
- 解析后的数据转换为系统内部表格结构
- 前端通过 WebSocket 将导入结果发送到服务端
- 服务端更新当前文档快照，并广播给其他在线用户

### 3.6 协同同步

- 至少支持 2 个用户进入同一张表格
- 其中一人修改单元格后，另一人可实时看到结果
- 服务端使用中心化房间模型和顺序广播保证同步顺序
- 同一单元格并发写入时，本期采用后写覆盖策略

## 5. 前端功能清单

### 5.1 身份模块

- 启动时生成临时身份

### 5.3 表格编辑模块

### 5.4 Excel 导入模块

- 选择本地文件

### 5.5 分享模块

### 5.6 协同模块

## 6. 后端功能清单

### 6.1 HTTP 接口

#### `GET /health`

- 用于健康检查
- 返回服务可用状态

#### `POST /docs`

- 创建新的表格文档
- 统一返回 `code`、`message`、`data`

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001"
  }
}
```

### 6.2 WebSocket 事件

WebSocket 事件用于完成表格页面的实时协同，职责如下：

- `join`：用户进入某个表格房间，并拿到当前文档快照
- `set_cell`：提交一次单元格内容修改
- `import_sheet`：提交一次整表导入结果，一期按整表替换处理
- `presence`：广播当前房间的在线用户，不负责同步文档内容或文档列表

这些事件共同组成一期的实时同步链路：进入房间、拉取当前状态、发送修改、接收广播、看到在线用户。
此外，一期还会为后续 `undo/redo` 做数据层铺垫，保留必要的历史版本信息。

#### `join`

客户端发送：

```json
{
  "type": "join",
  "docId": "doc_001",
  "clientId": "client_001",
  "userInfo": {
    "name": "用户001",
    "color": "#3b82f6"
  }
}
```

服务端响应：

```json
{
  "type": "join_ack",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "seq": 0,
    "snapshot": {
      "cells": {},
      "styles": {},
      "rowCount": 100,
      "colCount": 26
    },
    "users": []
  }
}
```

#### `set_cell`

客户端发送：

```json
{
  "type": "set_cell",
  "docId": "doc_001",
  "clientId": "client_001",
  "row": 1,
  "col": 1,
  "value": "hello"
}
```

服务端广播：

```json
{
  "type": "cell_updated",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "seq": 1,
    "clientId": "client_001",
    "row": 1,
    "col": 1,
    "value": "hello"
  }
}
```

#### `import_sheet`

说明：

- 一期将 `import_sheet` 定义为“整表替换”
- 导入成功后，当前文档原有表格内容会被新 `snapshot` 覆盖
- 这样实现最简单，也符合“导入一张表覆盖当前内容”的直觉

客户端发送：

```json
{
  "type": "import_sheet",
  "docId": "doc_001",
  "clientId": "client_001",
  "snapshot": {
    "cells": {
      "1:1": { "value": "姓名" },
      "1:2": { "value": "年龄" }
    },
    "styles": {},
    "rowCount": 20,
    "colCount": 10
  }
}
```

服务端广播：

```json
{
  "type": "sheet_imported",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "seq": 2,
    "clientId": "client_001",
    "snapshot": {
      "cells": {
        "1:1": { "value": "姓名" },
        "1:2": { "value": "年龄" }
      },
      "styles": {},
      "rowCount": 20,
      "colCount": 10
    }
  }
}
```

#### `presence`

说明：

- `presence` 只用于同步当前房间的在线用户
- 它不负责同步文档内容
- 它也不负责同步系统里有哪些文档

服务端广播：

```json
{
  "type": "presence",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "users": [
      {
        "clientId": "client_001",
        "name": "用户001",
        "color": "#3b82f6"
      }
    ]
  }
}
```

## 7. 数据模型建议

### 7.1 临时用户

```ts
type SessionUser = {
  clientId: string;
  name: string;
  color: string;
};
```

### 7.2 单元格与快照

```ts
type Cell = {
  value: string;
};

type SheetSnapshot = {
  cells: Record<string, Cell>;
  styles: Record<string, unknown>;
  rowCount: number;
  colCount: number;
};
```

### 7.3 文档结构

```ts
type SheetDoc = {
  docId: string;
  title: string;
  snapshot: SheetSnapshot;
  seq: number;
  createdAt: number;
  history: SnapshotHistoryEntry[];
};
```

```ts
type SnapshotHistoryEntry = {
  seq: number;
  snapshot: SheetSnapshot;
  createdAt: number;
  source: 'set_cell' | 'import_sheet';
};
```

## 8. 一期实现原则

- 优先打通“创建-进入-导入-编辑-同步-分享”主链路
- Excel 解析放在前端，不放在后端
- 后端先以内存存储为主
- 协同先采用房间广播和后写覆盖策略
- 一期额外保留历史快照，为后续 `undo/redo` 做铺垫
- 不为后续复杂能力提前设计过重架构

## 9. 关键实现细节

### 9.1 创建文档流程

一期推荐的创建文档流程如下：

1. 用户进入首页
2. 前端生成临时身份，并存入 `sessionStorage`
3. 用户点击“创建表格”
4. 前端调用 `POST /docs`
5. 后端生成新的 `docId`
6. 后端初始化一份空白文档快照
7. 后端返回 `docId`
8. 前端跳转到 `/sheet/:docId`
9. 表格页建立 WebSocket 连接并发送 `join`
10. 服务端返回当前文档 `snapshot`、`seq` 和在线用户列表

推荐的空白快照如下：

```json
{
  "cells": {},
  "styles": {},
  "rowCount": 100,
  "colCount": 26
}
```

### 9.2 分享链接说明

- 后端创建文档时返回的核心信息是 `docId`
- 前端基于路由规则拼接出文档访问地址
- 一期推荐路由为 `/sheet/:docId`
- 例如后端返回 `doc_123`，前端跳转到 `/sheet/doc_123`
- 分享时复制的完整链接通常为 `当前站点域名 + /sheet/:docId`

也就是说，所谓“分享链接”本质上是前端编辑页面地址和文档 ID 的组合，而不是后端单独生成一个特殊页面。

### 9.3 文档存储方式

开发阶段先采用纯内存存储方案。

一期当前阶段的文档状态以服务端内存为准，后端使用内存 `Map<string, SheetDoc>` 保存所有文档。

文档结构建议如下：

```ts
type SheetDoc = {
  docId: string;
  title: string;
  snapshot: SheetSnapshot;
  seq: number;
  createdAt: number;
  updatedAt: number;
  history: SnapshotHistoryEntry[];
};
```

其中：

- `snapshot` 表示当前整张表的最新状态
- `seq` 表示服务端当前已分配的最新操作序号
- `updatedAt` 用于标记最近一次变更时间
- `history` 用于保存历史快照，给后续 `undo/redo` 预留数据基础

开发阶段的实现方式如下：

- 后端用内存 `Map<string, SheetDoc>` 保存所有文档
- 创建文档时初始化空白 `snapshot`
- 用户编辑时直接修改内存中的当前文档状态
- 每次成功修改后，追加一条历史快照记录到 `history`
- 服务重启后数据会丢失，这属于开发阶段可接受范围

一期建议至少保留以下历史信息：

- 初始空白快照
- 每次 `set_cell` 成功后的快照
- 每次 `import_sheet` 成功后的快照

为避免历史无限增长，一期可以先采用简单策略：

- 仅保留最近 N 条历史快照
- 或只保留关键操作后的历史快照

### 9.4 多人协同与 JSON 快照的关系

需要明确：

- 多人协同不是让多个客户端直接并发修改同一个存储字段
- `snapshot` 只是当前文档状态的快照存储形式
- 实时协同依赖的是 WebSocket 操作流和服务端顺序处理
- 一期保存当前 `snapshot`、当前最新 `seq`，以及有限的历史快照

一期推荐采用赛题建议的“中心化房间 + 操作广播”模型：

1. 客户端产生编辑操作并发送给服务端
2. 服务端可为该操作分配递增 `seq`
3. 服务端按顺序把操作应用到当前文档内存状态
4. 服务端将该操作广播给房间内其他客户端
5. 客户端按服务端广播顺序更新本地状态；如果保留 `seq`，则可用它标记服务端确认顺序

这意味着：

- 服务端 WebSocket 房间负责多人编辑调度
- `snapshot` 负责保存当前最新状态，方便新用户加入时同步

### 9.5 `seq` 的含义与处理顺序

`seq` 是服务端生成的递增序号，不是前端生成的。

它的作用是：

- 标记每一次成功进入服务端处理流程的修改顺序
- 明确“后写”是以服务端确认顺序为准
- 作为当前文档状态的顺序编号，便于后续扩展
- 作为历史快照的顺序索引，便于后续实现 `undo/redo`

一期可以按下面的方式理解：

1. 前端发送一次修改请求
2. 服务端收到后，为这次修改分配下一个 `seq`
3. 服务端把修改应用到当前文档内存状态
4. 服务端立刻把这次修改广播给房间内所有客户端
5. 然后继续处理下一次修改请求

也就是说，一期的核心思路就是：

- 后端按顺序处理所有进入同一文档的修改请求
- 每处理完一次，就广播一次结果
- 所有客户端根据服务端广播的顺序更新本地状态

需要注意：

- 一期即使不保存历史版本快照，也可以保留 `seq`
- 当前方案中，一期会保存有限历史快照，`seq` 可作为这些历史记录的顺序编号
- 即使如此，`seq` 也不等同于完整的历史版本系统，它只是历史记录的基础索引

### 9.6 历史快照设计

为了给后续 `undo/redo` 做铺垫，一期建议在内存中保留有限历史快照。

推荐规则如下：

- 创建文档时写入一条初始快照，`seq = 0`
- 每次 `set_cell` 成功后，生成新的 `seq`，并把更新后的 `snapshot` 写入 `history`
- 每次 `import_sheet` 成功后，生成新的 `seq`，并把导入后的整表 `snapshot` 写入 `history`
- 一期先不实现真正的 `undo/redo` 行为，只准备后续可用的数据基础

如果后续要做 `undo/redo`，可以基于这些历史快照继续扩展：

- 回退到上一条历史快照
- 或基于历史快照和操作类型生成反向操作

### 9.7 冲突处理策略

赛题对 P0 的建议是：同一单元格并发写入时，采用后写覆盖策略。

一期建议明确如下规则：

- 两个用户同时修改同一个单元格时
- 以服务端先后接收顺序为准
- 后到达服务端的那次修改覆盖前一次修改
- 所有客户端最终都按服务端广播的 `seq` 顺序收敛到同一结果

这是一种 `LWW` 策略，适合作为一期最小可行方案。

## 10. 验收标准

第一期完成后，至少满足以下验收项：

- 打开首页后可获得一个临时身份
- 可以创建一张新表格
- 可以通过链接进入指定表格
- 可以复制分享链接给其他人
- 可以导入一个 Excel 文件并看到表格内容
- 可以修改单元格内容并提交
- 两个浏览器窗口可实时同步同一张表格的单元格修改
- 页面可显示当前在线用户
- 后端服务有健康检查接口
