# COLLAB

# **COLLAB 协同与一致性策略**



## **1\. 文档目标**

- 说明在线表格协同链路、前后端职责边界，以及当前一致性策略。

- 说明多人同时编辑同一文档时，系统如何完成连接建立、消息同步、版本推进和结果回写。

- 说明断线重连、离线补发、冲突处理、undo / redo 等场景下的协同处理方式。

- 作为前后端统一对齐协同协议、异常处理和一致性策略的说明文档。



## **2\. 架构设计和协同流程 \[向\]\[易\]**

### **2\.1 整体架构**

- 协同架构采用前端 WebSocket 客户端 \+ 后端房间广播服务的模式。

- 前端负责建立连接、发送协同消息、接收广播消息、更新本地 Store，并驱动界面重绘。

- 后端负责接收协同请求、维护文档实时态、推进版本号、广播操作结果，并完成异步持久化。

- 同一文档的在线用户进入同一个房间，围绕同一份文档快照和版本号进行协同。

### **2\.2 前后端职责划分**

- 前端 \[易\]：负责 WebSocket 全双工通信客户端（CollabClient）、14 种消息类型的收发分发（join / set_cell / batch_set_cell / set_range_values / set_title / undo / redo / insert_row / delete_row / insert_col / delete_col / cursor / import_sheet / add_sheet）、乐观更新（先更新本地 UI 再发 WS）、离线队列持久化（localStorage + 同格去重 + 500 条上限 + 跨文档过滤）、断线重连健壮性策略（指数退避 / 500ms 防抖 / connectAttemptId 防竞态 / visibilitychange 暂停）、重连后离线操作自动补发、同格冲突检测与用户裁决弹窗（ConflictDialog）、在线用户状态栏与光标位置广播、浏览器断网检测（navigator.onLine 拦截 + online/offline 事件自动恢复）。模块采用分层架构：collab/ 核心层 → hooks/ 桥接层 → components/ 表现层 → store/ 状态层，协同层与 Canvas 渲染层通过 Redux store 单向通信，职责严格分离。

- 后端 \[向\]：负责处理 `join`、`presence`、`cursor`、`set_cell`、`batch_set_cell`、`set_range_values`、`set_title`、`insert_row`、`delete_row`、`insert_col`、`delete_col`、`undo`、`redo`、`import_sheet`、`add_sheet` 等协同消息。

- 前端负责用户动作到协同消息的转换，后端负责协同消息到文档状态变更的落地。

- 前端负责本地展示和交互反馈，后端负责版本推进、冲突处理、广播和持久化。

### **2\.3 协同主流程**

- 用户进入文档页后，前端建立 WebSocket 连接，并发送 `join` 消息加入对应文档房间。

- 服务端返回当前文档快照、当前版本号和房间状态，前端用返回结果初始化本地协同状态。

- 用户执行编辑、批量修改、插删行列、撤销重做等操作后，前端将操作编码成对应协同消息并发送给服务端。

- 服务端接收请求后，按文档维度串行处理，完成参数校验、版本比较、OT 处理、快照更新和版本推进。

- 服务端为本次操作生成新的 `seq`，并把结果广播给房间内其他客户端。

- 各客户端收到广播后，按服务端返回结果更新本地 Store、协同状态和渲染结果。

- 服务端在完成实时态更新和广播后，再将持久化任务异步写入存储层。



## **3\. WebSocket 连接与前端协同状态 \[易\]**

### **3.1 连接建立与房间加入**

前端 CollabClient 负责 WebSocket 全生命周期管理。用户进入文档页后：

1. 通过 `new WebSocket(url)` 建立连接
2. 连接成功（`onopen`）后立即发送 `join` 消息，携带 `docId`、`clientId`、`name`、`color`
3. 服务端返回 `join_ack`，包含全量文档快照（`snapshot`）、当前版本号（`currentSeq`）和房间在线用户列表（`users`）
4. 前端用快照初始化本地 Redux store（`importWorkbook` + `setWorksheet`），版本号写入 `collabSlice.currentSeq`
5. 若本地存在离线队列，在 `join_ack` 后立即调用 `replayOfflineQueue()` 按序补发

```text
用户打开文档 → WS 连接 → join → join_ack(snapshot + seq + users)
  → 初始化 Redux → 渲染 Canvas → 开始接收操作广播
  → 有离线队列? → replayOfflineQueue()
```

### **3.2 在线状态管理**

前端通过 Redux `collabSlice` 维护连接状态：

| 状态 | 含义 | UI 表现 |
|------|------|---------|
| `connected` | WebSocket 已连接，正常通信 | 🟢 绿灯 |
| `disconnected` | WebSocket 断开（断网/手动离线） | ⚪ 灰灯 + 黄色横幅"网络已断开" |
| `reconnecting` | 断开后正在重试连接 | 🟡 黄灯 + 黄色横幅"正在重连…" |
| `failed` | 10 次重试全部失败 | 🔴 红灯 + 红色横幅"连接失败" |

服务端通过 `presence` 消息广播房间在线用户列表。前端收到后 dispatch `setOnlineUsers`，StatusBar 组件读取并渲染头像圆点和用户名。在线人数和头像变更由服务端 presence 广播驱动，客户端不自行修改用户列表。

光标位置通过 `cursor` 消息实时同步：用户移动选区时发送当前 `sheetId + row + col`，服务端广播 `cursor_update` 给房间内其他人。发送端做去重——同一位置不重复发送。

### **3.3 断线重连机制**

当 WebSocket `onclose` 触发时，前端进入重连流程：

- **500ms 防抖**：避免网络抖动时反复建连，`onclose` 后等待 500ms 再决定是否重连
- **指数退避**：重试间隔 1s → 2s → 4s → 8s → 16s → 30s（封顶），最多 10 次
- **竞态防护**：每次 `connect()` 生成新的 `connectAttemptId`，握手期间非最新的 `onopen` 自动关闭
- **页面后台暂停**：监听 `visibilitychange`，页面切后台暂停重连、切回前台立即重试
- **超限处理**：10 次失败后标记 `failed`，更新 UI 为红色横幅提示用户刷新页面

### **3.4 浏览器网络感知**

除 WebSocket 层面的断线检测外，前端还监听浏览器级网络事件：

- `window.addEventListener('offline')` → 立即更新连接状态为 `disconnected`
- `window.addEventListener('online')` → 关闭旧连接，重置重试计数，立即发起重连
- `send()` 方法在调用 `ws.send()` 前检查 `navigator.onLine`，若为 `false` 则跳过发送，将操作直接写入离线队列

这解决了 Chrome DevTools Network Offline 时 `ws.readyState` 仍为 `OPEN` 导致消息"伪发送"的问题——浏览器拦截了网络层，但 WebSocket 对象未感知断开，消息会被缓冲到网络恢复后意外发出。

### **3.5 消息收发与乱序处理**

前端 CollabClient 的 `handleMessage` 按消息类型（16 种服务端响应）分发到对应回调。核心机制：

- **顺序控制（`applyOrdered`）**：服务端按 `seq` 顺序广播，但 WebSocket 可能乱序到达。若收到的 `seq` 不是下一个期望值，暂存到 `pendingOps` Map；待前置操作到达后依次消费
- **幂等去重（`seenSeqs`）**：发送方会收到 `reply` + `broadcast` 两条同 `seq` 消息，靠 `seenSeqs` Set 去重
- **消息可靠性（`pendingMessages`）**：关键操作（`set_cell`、`batch_set_cell`、`set_range_values`）发送时生成 `eventId` 并加入 `pendingMessages` Map，收到服务端回执后清除；`onclose` 时将未确认消息写入离线队列防止丢失

### **3.6 信息不对称处理**

前端通过多种机制处理用户与系统状态之间的信息差：

- **join_ack 全量快照校准**：重连后服务端返回最新快照作为单一事实来源，覆盖本地状态后再补发离线操作
- **baseSeq 版本对比**：离线操作补发时，比较 `replayBaseSeq`（重连时的服务端 `seq`）与操作的 `baseSeq`（编辑时的版本号），检测离线期间是否有第三方插入操作
- **冲突弹窗**：检测到 `baseSeq` 间距后弹出 ConflictDialog，逐格展示"你的值 vs 在线用户的值"，让用户手动选择保留哪个
- **diff 通知**：重连用户回放的编辑、行列增删、撤销重做操作，在接收方弹出 toast 提示（"XX 修改了 A1"、"XX 在第 3 行前插入了一行"等），仅在重连后 5 秒窗口内显示，避免正常在线编辑时频繁打扰



## **4\. 协同操作与后端处理链路 \[向\]**

### **4\.1 协同操作范围**

- 后端统一处理的协同消息包括：`join`、`presence`、`cursor`、`set_cell`、`batch_set_cell`、`set_range_values`、`set_title`、`insert_row`、`delete_row`、`insert_col`、`delete_col`、`undo`、`redo`、`import_sheet`、`add_sheet`。

- 其中 `set_cell`、`batch_set_cell`、`set_range_values`、`set_title`、`insert_row`、`delete_row`、`insert_col`、`delete_col`、`undo`、`redo`、`import_sheet`、`add_sheet` 会作为文档写请求进入主链路。

- `join` 用于进入文档房间并获取当前快照与版本号。

- `presence` 和 `cursor` 用于同步在线状态、光标位置和选区信息。

- 每次成功写入都会推进文档版本号，并向房间内其他客户端广播结果。

|操作类型|处理内容|
|---|---|
|`join`|处理用户加入房间，返回当前文档快照、版本号和房间状态。|
|`presence`|处理在线状态同步。|
|`cursor`|处理协作者光标和选区位置同步。|
|`set_cell`|处理单个单元格的值或样式更新。|
|`batch_set_cell`|处理批量单元格更新。|
|`set_range_values`|处理批量单元格更新，以一次请求完成整批提交。|
|`set_title`|处理文档标题更新。|
|`insert_row`|处理插入行，并将结果写入历史记录。|
|`delete_row`|处理删除行，并将结果写入历史记录。|
|`insert_col`|处理插入列，并将结果写入历史记录。|
|`delete_col`|处理删除列，并将结果写入历史记录。|
|`undo`|按用户维度读取 undo 栈，生成新的写操作后再进入主链路。|
|`redo`|按用户维度读取 redo 栈，生成新的写操作后再进入主链路。|
|`import_sheet`|按整表级别更新当前工作表快照和版本号。|
|`add_sheet`|处理新增工作表并更新工作簿结构。|

### **4\.2 后端处理分层**

- WebSocket 接入层：接收前端消息，识别消息类型，完成基础参数校验。

- 消息分发层：按照消息类型把请求路由到对应的 handler 和 service。

- 业务处理层：执行加入房间、在线状态同步、光标同步、单元格更新、批量单元格更新、批量区域更新、标题修改、插入行、删除行、插入列、删除列、撤销、重做、导入工作表、新增工作表。

- 实时态层：维护当前文档的 `snapshot`、`currentSeq`、历史记录和用户级操作状态。

- 持久化层：将文档快照、历史记录和用户状态写入持久化存储。

### **4\.3 核心写入链路**

- 前端通过 WebSocket 发送协同消息，请求中携带文档标识、操作内容和 `baseSeq`。

- 服务端接收请求后，先校验文档 ID、sheet ID、row、col、value、版本号。

- 同一文档的请求进入串行处理或分布式锁保护区，按统一顺序执行。

- 服务端读取当前实时文档状态，包括 `currentSeq`、快照、历史操作和用户运行时状态。

- 服务端比较 `baseSeq` 和 `currentSeq`，必要时结合中间历史执行 OT / transform。

- 服务端将操作应用到当前文档快照，生成新的 `seq`，并更新 Redis 中的实时态。

- 服务端将最新结果广播给房间内其他客户端。

- 服务端把持久化任务写入异步队列，由后台 consumer 再写入 MySQL。

### **4\.4 实时态与持久化**

- Redis 维护协同过程中的实时文档状态，包括快照、版本号、历史记录和用户操作状态。

- Redis Stream 负责承接异步持久化任务。

- MySQL 负责保存最终快照、历史记录、用户状态和审计数据。

- 协同请求先更新实时态并完成广播，再异步写入持久化存储。



## **5\. 一致性与冲突处理策略 \[向\]**

### **5\.1 一致性基线**

- 服务端维护当前文档版本号 `currentSeq`，并作为最终版本顺序来源。

- 客户端发送写请求时携带本次编辑所基于的版本号 `baseSeq`。

- 同一文档的写请求按统一顺序处理，并在成功后生成新的 `seq`。

- 客户端以服务端广播结果为准更新本地状态。

### **5\.2 当前冲突处理策略**

- 当前方案采用 `OT / transform + LWW`。

- `OT / transform` 负责处理坐标变换。

- `LWW` 负责处理同一位置的最终值覆盖。

- 结构型操作进入历史记录，供后续请求执行 transform。

- 批量写操作在一次提交内共享同一个 `seq`。

### **5\.3 版本推进与对齐**

- 前端发起写请求时提交 `baseSeq`。

- 服务端读取当前 `currentSeq` 并比较版本差异。

- 如果 `baseSeq < currentSeq`，服务端读取中间历史并执行 OT 操作。

- 如果 OT 操作 成功，服务端将操作应用到当前快照。

- 服务端提交成功后生成新的 `seq`，并写入实时态与历史记录。

- 服务端向房间内客户端广播本次操作结果。

- 客户端收到广播后，以服务端结果对齐本地状态。

### **5\.4 冲突类型与处理方式**

当前值冲突按单元格粒度处理，不处理单元格内字符级合并。

- 同一单元格被多人修改时，按服务端接收顺序提交，最终值采用 LWW。

- 插入行、删除行、插入列、删除列之后再编辑单元格时，服务端会根据 `baseSeq` 到 `currentSeq` 之间的历史操作执行 OT 操作，修正目标坐标。

- 离线操作在重连后补发时，先基于最新快照恢复连接，再按中间历史执行 OT 操作，修正目标坐标。

- `undo` / `redo` 遇到中间结构变更时，先读取历史栈，再按当前文档状态执行 OT 操作，最后作为新写操作提交。

- `import_sheet` 与旧快照上的离线编辑并发时，视为不可直接合并的场景，返回冲突并要求客户端刷新。



## **6\. 断线恢复与异常处理 \[向\]\[易\]**

### **6\.1 前端处理 \[易\]**

前端覆盖了从网络断开到消息丢失、从并发冲突到存储耗尽的完整异常边界：

**离线编辑不丢失**

断线时 `set_cell` / `batch_set_cell` / 行列增删操作写入 `localStorage` 离线队列（OfflineQueue），支持：

- **同格去重**：同一单元格只保留最后一次操作，旧操作被覆盖
- **500 条上限**：超出后移除最旧条目，防止 localStorage 爆满
- **跨文档过滤**：重连回放时只发送当前文档的操作，其他文档的操作放回队列
- **时效过滤**：忽略无时间戳的旧数据和 5 秒内新产生的操作（由 `flushPendingToOfflineQueue` 写入的未确认消息，避免重复回放）

重连后收到 `join_ack`，先以服务端快照覆盖本地状态，再按序补发离线队列中的操作。行列操作也支持离线持久化，断线期间的增删行列不会丢失。

**消息可靠性确认**

`WebSocket.send()` 是异步的，TCP 发出不代表服务端收到。关键操作发送时携带 `eventId`，`pendingMessages` Map 追踪所有未确认消息。收到服务端回执（`cell_updated` / `batch_cell_updated` / `range_values_updated` 中的 `eventId`）后清除。`onclose` 时将未确认消息写入离线队列（`flushPendingToOfflineQueue`），覆盖 `set_cell` 和 `batch_set_cell` 类型。

**断线重连健壮性**

详见 3.3 节。关键参数：指数退避 1s→30s、最多 10 次、500ms 防抖、connectAttemptId 竞态防护、visibilitychange 后台暂停。

**同格冲突用户感知**

离线操作补发后，通过 `baseSeq` 与 `currentSeq` 的间距检测中间是否有第三方操作。检测到冲突弹出 `ConflictDialog`，逐格展示"你的值 vs 在线用户的值"，用户逐格选择保留哪个。5 秒超时兜底：服务端回执未收齐时按已收到的判断。此冲突是交互层面的"信息不对称"而非协同算法冲突——LWW 已决定最终值，弹窗让被覆盖方知晓。

**存储边界防护**

`localStorage.setItem` 失败时（存储满或浏览器限制），`OfflineQueue.saveAll` 返回 `false`，触发 `onError` 回调弹出提示"离线存储空间不足，请清理浏览器数据"。首次提示后去重（`storageWarned` 标志），同一会话不反复骚扰。

**防御性数据接收**

所有远端回调中对 `value` 字段做存在性检查（`'value' in data`）。服务端为节省带宽可能在仅改样式时不传 `value`，前端从本地 store 读取当前格原值兜底，避免被 `undefined` 覆盖为空白。

**浏览器网络感知**

除 WebSocket 层面的 `onclose` 外，前端同时监听 `window` 的 `offline` / `online` 事件，并在 `send()` 方法中检查 `navigator.onLine`。这解决了 Chrome DevTools Network Offline 时 `ws.readyState` 仍为 `OPEN` 导致消息意外发出的问题。浏览器恢复在线后自动关闭旧连接、重置重试计数、立即发起重连。

- 后端在客户端重连后返回最新文档快照、当前版本号和房间状态，作为恢复基线。

- 后端继续按 `baseSeq` 和 `currentSeq` 比较版本差异，并对可恢复的离线操作执行 OT 操作。

- 后端对重复提交、过期请求和非法参数请求进行校验，避免重复写入和错误写入。

- 后端对 `import_sheet` 这类不可直接合并的场景返回冲突结果，由前端提示用户刷新。

- 后端在客户端断开后更新在线状态和房间成员信息，保证 `presence` 数据及时收敛。

- 后端在实时态更新成功后再广播协同结果，持久化失败时通过异步队列重试，保证最终落库。



## **7\. undo / redo 与协同 \[向\]\[易\]**

### **7\.1 后端处理 \[向\]**

- 后端按 `docId + clientId` 维度维护独立的 `undo` 栈和 `redo` 栈。

- 普通写操作成功提交后，会把对应操作记录压入 `undo` 栈，并清空 `redo` 栈。

- 用户发起 `undo` 时，服务端读取当前用户的 `undo` 栈，取出栈顶记录，并根据记录中的旧值或旧状态构造恢复操作。

- 用户发起 `redo` 时，服务端读取当前用户的 `redo` 栈，取出栈顶记录，并根据记录中的新值或新状态重新构造提交操作。

- `undo` 和 `redo` 不直接回退本地状态，而是作为新的写操作重新进入文档主链路。

- 在重新提交前，服务端会基于当前文档状态和中间历史执行 OT 操作，修正行列结构变更带来的坐标漂移。

- 处理成功后，服务端会为本次 `undo` 或 `redo` 生成新的 `seq`，写入实时态和历史记录，并广播给房间内其他客户端。

- `undo` 成功后，服务端会把对应反向记录压入 `redo` 栈；`redo` 成功后，服务端会把对应反向记录压回 `undo` 栈。

### **7\.2 前端处理 \[易\]**

前端 undo/redo 操作为纯透传——不本地构造逆向操作，不维护历史栈：

1. 用户触发 undo → 前端发送 `{ type: 'undo' }` 消息
2. 服务端执行完整 undo 逻辑（见 7.1）→ 生成新的写操作 → 广播 `undo_applied`
3. 前端在 `onUndoApplied` 回调中更新对应单元格的 Redux state，UI 自动重绘

redo 流程同理（`redo` → 服务端处理 → `redo_applied`）。

前端不在本地做 undo/redo 的原因：服务端已按 `docId + clientId` 维度维护了权威的 undo/redo 栈，且 undo/redo 涉及 OT 坐标变换（还原时的行列结构可能已变化），服务端侧执行能确保正确性。

离线期间的 undo/redo 操作目前不进入离线队列（待后续优化），因为 undo/redo 依赖服务端的操作栈，客户端无法在离线时确定可撤销的操作。



## **8\. 当前方案总结与后续优化 \[向\]\[易\]**

### 8\.1 当前方案总结

- 当前协同方案采用前端 WebSocket 客户端 \+ 后端房间广播服务的整体架构。

- 前端负责连接管理、消息发送与接收、本地状态更新、断线重连和离线补发。

- 后端负责协同消息处理、文档实时态维护、版本推进、冲突处理、广播和异步持久化。

- 一致性策略上，当前采用 `OT / transform + LWW` 的方式：OT 负责处理插入行列、删除行列带来的坐标变化，LWW 负责同一单元格的最终值覆盖。

- 在写链路上，协同操作统一进入同一条主链路，按文档维度串行处理，并以 `seq` 推进版本，保证各客户端最终结果一致。

- 在异常处理上，前端负责断线恢复、消息重试和离线补发，后端负责恢复基线返回、冲突校验和不可合并场景兜底。

### 8\.2 当前方案边界

- 当前值冲突按单元格粒度处理，不处理单元格内字符级合并。

- 当前 OT 主要处理行列结构变更带来的坐标修正，不覆盖更细粒度的文本协同。

- `import_sheet` 这类整表替换操作与旧快照上的离线编辑不做直接合并。

- 离线补发场景下，如果历史跨度过大或中间存在不可恢复冲突，仍需要前端提示用户刷新页面重新同步。

### 8\.3 后续优化方向

- 协同粒度优化：从单元格级协同继续向字符级协同演进，提升同格多人编辑体验。\[向\]
