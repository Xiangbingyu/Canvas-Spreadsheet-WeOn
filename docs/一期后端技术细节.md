# 第一期后端技术细节

## 1. 一期后端目标

第一期后端需要完成以下能力：

1. 提供基础健康检查接口
2. 提供创建表格文档接口
3. 为表格详情页提供 WebSocket 房间协同能力
4. 支持用户加入文档房间并返回当前快照
5. 支持单元格文本修改的实时广播
6. 支持 Excel 导入后的整表替换广播
7. 支持当前房间在线用户同步
8. 在内存中保存当前快照、`seq` 和有限历史快照

## 2. 技术选型

结合当前仓库结构和一期范围，后端建议采用以下技术栈：

- 运行时：Node.js
- Web 框架：Express
- 协同通信：WebSocket
- 数据存储：服务端内存 `Map`
- 数据格式：JSON

说明：

- 当前 `backend-js` 已经初始化为 `Express` 项目，适合作为一期后端骨架
- 一期优先追求最小闭环，不引入数据库
- 一期优先使用中心化房间模型，不引入 CRDT/OT

## 3. 一期后端职责

后端在一期的职责主要有四类：

- HTTP 接口：创建文档、健康检查
- WebSocket 协同：加入房间、编辑广播、导入广播、在线状态同步
- 内存存储：保存当前文档状态
- 历史记录：为后续 `undo/redo` 预留基础数据

后端在一期不负责的内容：

- 正式登录注册
- 持久化数据库
- 权限系统
- 复杂冲突处理
- 公式计算
- Excel 文件解析

其中 Excel 解析由前端完成，后端只接收前端转换后的 `snapshot`。

## 4. 统一响应规范

为了避免前后端联调时响应字段不统一，一期后端建议统一使用响应包裹结构。

### 4.1 HTTP 响应结构

HTTP 接口统一返回：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

字段约定：

- `code`：业务状态码，`0` 表示成功，非 `0` 表示失败
- `message`：接口说明或错误信息
- `data`：实际业务数据，成功时返回对象，失败时可为 `null`

成功示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001"
  }
}
```

失败示例：

```json
{
  "code": 4004,
  "message": "Document not found",
  "data": null
}
```

### 4.2 WebSocket 消息结构

WebSocket 消息建议也采用统一包裹格式：

```json
{
  "type": "join_ack",
  "code": 0,
  "message": "ok",
  "data": {}
}
```

字段约定：

- `type`：消息类型
- `code`：业务状态码，`0` 表示成功
- `message`：结果说明
- `data`：消息体内容

这样做的好处：

- 前端处理 HTTP 和 WebSocket 时心智一致
- 成功消息和错误消息结构统一
- 后续扩展错误码、调试日志和监控更方便

### 4.3 一期推荐错误码

一期可以先约定一套简单错误码：

- `0`：成功
- `4000`：参数错误
- `4001`：消息类型不支持
- `4004`：文档不存在
- `5000`：服务端内部错误

## 5. HTTP 接口设计

### 5.1 `GET /health`

用途：

- 健康检查
- 前后端联调时快速确认服务是否正常

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "status": "ok"
  }
}
```

### 5.2 `POST /docs`

用途：

- 创建一个新的空白表格文档

处理流程：

1. 生成新的 `docId`
2. 初始化空白 `snapshot`
3. 初始化 `seq = 0`
4. 初始化一条历史快照记录
5. 将新文档写入内存 `Map`
6. 返回 `docId`

响应示例：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001"
  }
}
```

推荐的空白快照：

```json
{
  "cells": {},
  "styles": {},
  "rowCount": 100,
  "colCount": 26
}
```

## 6. WebSocket 事件设计

一期后端 WebSocket 主要围绕以下四类事件：

- `join`
- `set_cell`
- `import_sheet`
- `presence`

这四类事件共同组成一期协同主链路。

### 6.1 `join`

用途：

- 用户进入某个文档房间
- 服务端返回当前文档状态和在线用户

客户端发送：

```json
{
  "type": "join",
  "docId": "doc_001",
  "clientId": "client_001",
  "userInfo": {
    "name": "用户001",
    "color": "#3b82f6"
  }
}
```

服务端处理：

1. 校验 `docId` 是否存在
2. 将当前连接加入该文档房间
3. 把当前用户加入房间在线用户集合
4. 返回当前文档 `snapshot` 和 `seq`
5. 广播最新 `presence`

服务端响应：

```json
{
  "type": "join_ack",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "seq": 0,
    "snapshot": {
      "cells": {},
      "styles": {},
      "rowCount": 100,
      "colCount": 26
    },
    "users": []
  }
}
```

### 6.2 `set_cell`

用途：

- 提交一次单元格文本修改

客户端发送：

```json
{
  "type": "set_cell",
  "docId": "doc_001",
  "clientId": "client_001",
  "row": 1,
  "col": 1,
  "value": "hello"
}
```

服务端处理：

1. 读取目标文档
2. 为本次修改分配新的 `seq`
3. 修改内存中的 `snapshot`
4. 将修改后的完整快照写入 `history`
5. 广播本次修改结果

服务端广播：

```json
{
  "type": "cell_updated",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "seq": 1,
    "clientId": "client_001",
    "row": 1,
    "col": 1,
    "value": "hello"
  }
}
```

### 6.3 `import_sheet`

用途：

- 接收前端解析后的整表数据
- 用导入结果替换当前文档的表格内容

一期约定：

- `import_sheet` 按整表替换处理
- 导入成功后，当前文档原有内容会被新的 `snapshot` 覆盖

客户端发送：

```json
{
  "type": "import_sheet",
  "docId": "doc_001",
  "clientId": "client_001",
  "snapshot": {
    "cells": {
      "1:1": { "value": "姓名" },
      "1:2": { "value": "年龄" }
    },
    "styles": {},
    "rowCount": 20,
    "colCount": 10
  }
}
```

服务端处理：

1. 读取目标文档
2. 分配新的 `seq`
3. 用新 `snapshot` 替换当前文档快照
4. 将替换后的完整快照写入 `history`
5. 广播整表导入结果

服务端广播：

```json
{
  "type": "sheet_imported",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "seq": 2,
    "clientId": "client_001",
    "snapshot": {
      "cells": {
        "1:1": { "value": "姓名" },
        "1:2": { "value": "年龄" }
      },
      "styles": {},
      "rowCount": 20,
      "colCount": 10
    }
  }
}
```

### 6.4 `presence`

用途：

- 广播当前房间在线用户

说明：

- `presence` 只同步当前房间在线用户
- 不同步文档内容
- 不同步系统中有哪些文档

服务端广播：

```json
{
  "type": "presence",
  "code": 0,
  "message": "ok",
  "data": {
    "docId": "doc_001",
    "users": [
      {
        "clientId": "client_001",
        "name": "用户001",
        "color": "#3b82f6"
      }
    ]
  }
}
```

## 7. 内存存储设计

一期后端采用纯内存存储。

推荐结构：

```ts
type Cell = {
  value: string;
};

type SheetSnapshot = {
  cells: Record<string, Cell>;
  styles: Record<string, unknown>;
  rowCount: number;
  colCount: number;
};

type SnapshotHistoryEntry = {
  seq: number;
  snapshot: SheetSnapshot;
  createdAt: number;
  source: 'set_cell' | 'import_sheet';
};

type RoomUser = {
  clientId: string;
  name: string;
  color: string;
};

type SheetDoc = {
  docId: string;
  title: string;
  snapshot: SheetSnapshot;
  seq: number;
  createdAt: number;
  updatedAt: number;
  history: SnapshotHistoryEntry[];
};
```

推荐的服务端内存结构：

```ts
const docs = new Map<string, SheetDoc>();
const roomUsers = new Map<string, Map<string, RoomUser>>();
const roomSockets = new Map<string, Set<WebSocket>>();
```

说明：

- `docs` 保存文档当前状态
- `roomUsers` 保存每个文档房间的在线用户
- `roomSockets` 保存每个文档房间的连接集合

## 8. `seq` 与历史快照

### 7.1 `seq` 的作用

`seq` 是服务端生成的递增序号，不由前端生成。

它的用途包括：

- 标记服务端确认的修改顺序
- 明确后写覆盖的顺序依据
- 为历史快照提供顺序索引
- 为后续 `undo/redo` 提供基础编号

### 7.2 一期处理方式

一期可按以下流程理解：

1. 客户端发起一次修改
2. 服务端读取目标文档
3. 服务端为本次修改生成新的 `seq`
4. 服务端更新内存快照
5. 服务端将更新后的快照写入 `history`
6. 服务端广播处理结果

也就是说：

- 后端按顺序处理进入同一文档的修改请求
- 每处理完一次，就广播一次结果
- 所有客户端根据服务端广播顺序收敛到同一状态

### 7.3 历史快照策略

一期后端虽然不实现真正的 `undo/redo`，但需要保留有限历史快照，为后续扩展做准备。

推荐策略：

- 创建文档时写入初始空白快照
- 每次 `set_cell` 成功后写入一条历史快照
- 每次 `import_sheet` 成功后写入一条历史快照

为了避免内存无限增长，一期建议：

- 仅保留最近 N 条历史快照
- N 可以先设为 20、50 或 100

## 9. 冲突处理与协同策略

一期采用中心化房间 + 顺序广播模型。

冲突处理策略：

- 同一单元格并发修改时，采用后写覆盖
- “后写”的定义以服务端确认顺序为准
- 更大的 `seq` 代表更晚确认的修改

示例：

1. 用户 A 修改 `A1 = foo`
2. 用户 B 修改 `A1 = bar`
3. 服务端先处理 A，分配 `seq = 10`
4. 服务端后处理 B，分配 `seq = 11`
5. 最终所有客户端都以 `seq = 11` 对应的结果为准

这样可以满足一期最小协同要求。

## 10. Express 服务组织建议

结合当前 `backend-js` 结构，一期建议按以下方向组织后端代码：

```text
backend-js/
  app.js
  server.js
  routes/
    docs.js
    health.js
  ws/
    index.js
    handlers/
      join.js
      setCell.js
      importSheet.js
      presence.js
  store/
    docsStore.js
    roomsStore.js
  services/
    docsService.js
    historyService.js
  utils/
    createDocId.js
    createSnapshot.js
    cloneSnapshot.js
```

职责建议：

- `app.js`：创建 Express 实例，注册中间件和 HTTP 路由
- `server.js`：启动 HTTP 服务，并挂载 WebSocket 服务
- `routes/`：处理 HTTP 请求入口
- `ws/handlers/`：处理各类 WebSocket 事件
- `store/`：保存内存状态
- `services/`：封装文档修改、历史记录等核心逻辑

## 11. 一期异常处理

后端至少需要覆盖以下异常场景：

- 创建文档失败
- `docId` 不存在
- `join` 时文档不存在
- WebSocket 消息格式非法
- `set_cell` 参数缺失
- `import_sheet` 缺少合法 `snapshot`

建议处理方式：

- HTTP 接口返回明确状态码和错误信息
- WebSocket 返回统一错误事件，例如 `error`
- 服务端日志记录关键异常，便于联调排查

示例：

```json
{
  "type": "error",
  "code": 4004,
  "message": "Document not found",
  "data": null
}
```

## 12. 一期验收视角

从后端视角看，一期完成的标准至少包括：

- `GET /health` 可正常返回
- `POST /docs` 可创建新文档并返回 `docId`
- 客户端可以通过 `join` 获取当前文档快照
- `set_cell` 可更新文档并广播给其他客户端
- `import_sheet` 可执行整表替换并广播
- `presence` 可正确广播当前在线用户
- 服务端内存中能保存当前快照、`seq` 和有限历史快照

## 13. 二期演进方向

第一期后端完成后，建议按以下顺序继续演进：

1. 引入数据库持久化文档
2. 将历史快照优化为“操作日志 + 周期快照”
3. 支持 `undo/redo` 协同策略
4. 增加增删行列操作
5. 增加样式修改操作
6. 优化多实例部署与一致性方案

## 14. 一期结论

第一期后端的核心不是做复杂业务平台，而是先把以下主链路做稳定：

- 创建文档
- 加入房间
- 返回当前快照
- 实时编辑广播
- 整表导入广播
- 在线用户同步
- 历史快照铺垫

在这个基础上，后端采用 `Express + WebSocket + 内存存储` 就足够支撑一期演示，并且能为后续 `undo/redo`、样式操作和持久化扩展保留空间。
