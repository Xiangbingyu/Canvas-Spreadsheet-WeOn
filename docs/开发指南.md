# 开发指南（组长 / 全员）

本文说明如何在「前后端同一仓库」下协作，避免常见的环境不一致、依赖混乱、合并冲突问题。

## 1. 为什么用 monorepo

| 做法              | 说明                                             |
| ----------------- | ------------------------------------------------ |
| 一个 Git 仓库     | 需求、接口、代码版本对齐，评审/演示只 clone 一次 |
| 根目录 `pnpm dev` | 新人一条命令跑起全栈                             |
| `docs/` 集中文档  | 组长维护需求与接口，减少口头传递                 |

子目录职责：

- `frontend/` — 只放 UI、状态、Canvas 渲染、与后端的 HTTP/WS 客户端
- `backend-js/` — 只放 API、WebSocket、存储与业务逻辑
- `docs/` — 功能清单、接口约定（**改接口前先改文档**）

## 2. 环境统一

1. 安装 **Node 22.12.0**（可用 nvm / fnm，仓库根目录有 `.nvmrc`）
2. 使用 **pnpm**，在**仓库根目录**执行 `pnpm install`
3. 不要在 `frontend` 或 `backend-js` 里单独执行 `npm install`
4. 复制 `.env.example` 为 `.env`（两边各一份），**不要提交 `.env`**

若有人本机端口被占用，只改自己 `.env` 里的 `PORT`，并同步告知前端 proxy 配置（见 `frontend/vite.config.ts`）。

## 3. Git 分支策略

```
main          ← 可演示、稳定版本
  └── develop ← 日常集成（默认合并目标）
        ├── feature/fe-canvas-render   ← 前端同学
        ├── feature/be-ws-sync         ← 后端同学
```

规则建议：

- **禁止**直接向 `main` push；通过 Pull Request
- 分支命名：`feature/简短描述`、`fix/问题描述`
- 合并前在根目录执行：`pnpm lint`、`pnpm build`（前端改动时）

## 4. 前后端对接

### HTTP

- 后端路由前缀：`/health`、`/docs`（见 `backend-js/routes/`）
- 开发环境：前端请求**相对路径**（如 `/health`），由 Vite proxy 转到 `localhost:3000`
- 生产环境：通过 `frontend/.env` 的 `VITE_API_BASE_URL` 配置完整后端地址

### WebSocket

- 开发：连 `ws://localhost:5173/ws`（由 Vite 代理到后端）或按文档约定
- 消息格式以 `docs/一期后端技术细节.md` 为准；**变更需双方确认并更新文档**

## 5. 提交信息规范

```
<type>(<scope>): <简短说明>

type: feat | fix | docs | refactor | chore
scope: fe | be | docs | root
```

示例：

- `feat(be): 实现 join 房间 WS 处理`
- `feat(fe): 表格 Canvas 单元格绘制`

## 6. 代码风格

- 根目录已配置 **EditorConfig**、**Prettier**、**Husky + lint-staged**
- 提交前会自动格式化 `frontend` 下改动的文件
- VS Code/Cursor 打开仓库根目录时会提示安装推荐扩展（`.vscode/extensions.json`）
